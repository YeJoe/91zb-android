# 8.5.3 接口现状（2026-10-29 复核，基准文档）

> 这篇是**当前的唯一事实基准**。早期文档（`明文接口突破.md`、`直播接口清单.md`、`真人直播间筛选.md`
> 等）写于 8.5.3 的接口还没被复核之前，里面对「房间列表」的判断**已经失效**，以本文为准。
>
> 复核方式：一次全接口抓包（18060 包 / 113 条 flow，源 App 冷启动 → 切分类 → 进房 → 退出）
> \+ 17 个本地端口逐个手打接口。抓包与样本留在 `assets/archive/`。

---

## 0. 一句话

**8.5.3 没有「房间列表」接口了。** `/room/list` 在所有本地端口一律 404，源 App 冷启动全程一次都没调用它。
现在唯一能拿到房间数据的批量接口是 `POST /room/get_list_by_ids`——**它要你先给房间号**。
所以「列出大厅」这件事，只能靠一份房间号池 + 批量刷新详情来复现。

---

## 1. 接口存活表

| 接口 | 状态 | 实测 |
|---|---|---|
| `POST /room/list` | ❌ **已下线** | 17 个本地监听端口全部 404；抓包里从未出现 |
| `POST /room/get_list_by_ids` | ✅ **唯一可用** | `{"ids":"123,456"}` → `{"code":0,"rooms":[…]}`，200 个 id 约 0.5s |
| `POST /login/get_data_by_tbname` `{"tb_name":"lobby_menu"}` | ✅ | 34 条分类（真人区 5/101/102/103/104/105/108） |
| `POST /login/get_data_by_tbname` `{"tb_name":"item"/"vip"/"notice"}` | ✅ | 配置类静态表 |
| `POST /login/get_data_by_tbname` `{"tb_name":"room"}` | ❌ | `{"code":-2,"msg":"查询失败"}`——room 是动态表，不对外 |
| `POST /user_follow/my_follow` | ✅ **可用**（2026-10-29 更正） | 回 `podcast_id` + `nickname` + `avatar`；**`podcast_id` 就是房间号**，8/8 能命中房间，见 §6.5 |
| `POST /login/quick` | ❌ 需要 `apns_code` | 传空串或假值直接断连，**无法免 root 自助换 token** |
| `POST /room/get_info_by_ids` | ❌ | 老版本接口，8.5.3 里不存在（早期文档里写过，实际是 `get_list_by_ids`） |
| `WS /tunnel/open` | ✅ | 明文 HTTP 代理协议，见 `明文长连接通道.md` |

> 注意 `get_list_by_ids` 的 `ids` 是**逗号分隔的字符串**，不是数组。空 ids 会回
> `{"code":-1,"msg":"ids is null"}`——这个响应**不带 `rooms` 键**，所以拿它当端口探针判据会误判，
> 必须用真实房间号探。

## 2. 大厅列表去哪了

源 App 自己也不再问服务端要列表了。它维护一张本地表：

```
SharedPreferences: localData  →  key = "room.<uid>"  →  1972 条房间 JSON
```

这张表靠 WS 推送增量维护（`{"opt":"u","ctl":"room",…}`），切分类只是对本地表做**本地过滤**
（`menu_id` 匹配 + 按人气排序），全程不发请求。这也是为什么：

- 抓包里看不到任何「拉列表」的请求；
- 6 分钟 WS 监听也没等到一次性全量快照（隧道被源 App 独占，我们只能旁观增量）；
- App 启动瞬间就能出列表——数据本来就在磁盘上。

## 3. 我们的复现方式：id 池 + 批量刷新

既然服务端只认「你告诉我房间号」，那就先备一份房间号池：

| 环节 | 做法 |
|---|---|
| **种子** | 从源 App 的 `localData:room.423344474` 导出 **1972 个房间号**，打包成 `app/src/main/assets/room_ids.txt` |
| **落地** | App 首次启动拷到 `filesDir/room_ids.txt`，之后**只增不减**（刷新见过的新号并回去，缓存里的号也并回来） |
| **刷新** | 按 **250 个/批** 切片，**3 批一波** 并发打 `get_list_by_ids`，只留 `on_air=1` |
| **实测** | 1972 个 id → **1943 间在播**，首次 5.8s（含端口探测 3.9s），之后走端口缓存约 2s |

房间号是主播建房时就固定下来的，不是每次开播重新分配，所以池子相当稳定。

> **已知局限（必须写清楚）**：池子是静态种子，**新主播新建的房间号发现不了**。
> 源 App 没有「列表底部无限加载」，也就没法靠翻页扩充。想补新号只能在源 App 里逛到新房间时记下来手动追加。

## 4. 双凭证：两个都不可少

| 凭证 | 形态 | 从哪来 | 生命周期 |
|---|---|---|---|
| `?token=` | 32 位 hex | **只在内存**。8.5.3 起不落盘，必须 root + `tcpdump -i lo`，且**冷启动**（`am force-stop` 后重开）才抓得到 | App 重启即失效 |
| `authorization: Bearer` | JWE，330 字符 | prefs 的 `MAINUSER_DATA.token`，磁盘上有 | 跟登录态走，较长 |

> **JWE 正则的坑**：`alg=dir` 时 `encrypted_key` 段是**空的**，token 里会出现 `…In0..UL92…` 这种连续两个点。
> 正则必须写成 `[A-Za-z0-9_-]*`（`*` 而非 `+`），否则一条合法 JWE 会被判为非法——
> `tools/token_export.py` 早期「找不到 shared_prefs / 找不到 token」的误报就是它引起的。

## 5. 端口：每次重启都变，别写死

实测序列：`38481 → 45209 → 33297 → 38103 → 36909`（同一台机器，每次重启源 App 换一个）。

- 枚举：读 `/proc/net/tcp` 里状态 `0A`（LISTEN）的端口，排除 `5555`（adbd）；
- 判定：**不能用 `/room/list` 探**（已下线，所有端口 404）。用**真实房间号**打
  `/room/get_list_by_ids`，认响应里有 `rooms` 键的才是对的 vhost；
- 缓存：探测结果存 `prefs.tunnelPort`，60 秒内不重复扫；整体失败时强制重探一次（源 App 多半重启过）。

## 6. 分类表（`lobby_menu`，34 条里的真人区）

| `menu_id` | 名称 | 层级 | | `menu_id` | 名称 | 层级 |
|---|---|---|---|---|---|---|
| 1 | 关注 | 一级 tab | | 101 | 星秀 | 二级分类 |
| 2 | 推荐 | 一级 tab | | 102 | 女神 | 二级分类 |
| 3 | 热门 | 一级 tab | | 103 | 颜值 | 二级分类 |
| 4 | 附近 | 一级 tab | | 104 | 交友 | 二级分类 |
| 5 | 新人 | 二级分类 | | 105 | 音乐 | 二级分类 |
| 8 | 游戏 | 二级分类 | | 108 | 舞蹈 | 二级分类 |

**关键：房间对象的 `menu_id` 只会是 8 / 101~105 / 108，从来不会是 1/2/3/4。**
600 间样本实测分布：`8`×246、`103`×105、`101`×100、`104`×79、`102`×44、`108`×19、`105`×7。

也就是说 1/2/3/4 是**大厅顶部那排 tab**，不是房间属性，不能用它筛「附近」：

| 一级 tab | 源 App 怎么来的 | 我们的做法 |
|---|---|---|
| 关注 | 账号关注关系（服务端筛） | 本地收藏 ∪ `/user_follow/my_follow` |
| 推荐 | 服务端算法下发 | 没有列表接口 → 本地模拟：人气分 6 档，档内按房间号哈希打散 |
| 热门 | 人气降序 | 本地排序，口径一致 |
| 附近 | 服务端按定位下发 | 拿不到坐标 → 降级为**同城**，按 `city_show` 筛 |

进房参数里的 `menu_id`（`join{menu_id:3}`）是「从哪个 tab 点进来的」，与房间自身分类无关，
别拿它当分类依据。

## 6.5 关注：`podcast_id` 就是房间号

`POST /user_follow/my_follow {}` → `{"count":8,"result":[{podcast_id, nickname, avatar, …}]}`

- **`podcast_id` 拿去 `/room/get_list_by_ids` 能直接命中房间**，实测 8/8 命中，返回的
  `attachment_url` 与关注列表里的头像逐字节一致。所以不需要任何 id 映射表。
- 不分页：`page` / `pageIndex` / `offset` 传什么值都只回同一批。
- 返回体里没有房间号字段，只有 `podcast_id` —— 这就是为什么早期判断「关注拿不到房间号」是错的。
- 8 位关注里 7 位在播、1 位离线，`get_list_by_ids` 会把离线的也返回（`on_air=0`），
  所以要按 `on_air` 过滤才能拿去铺列表。

## 6.6 大厅列表去哪了

`/room/list` 已全端口下线，源 App 维护 `localData:room.<uid>` 本地表（实测 1972 间 / 1956 在播），
靠 WS `ctl=room` 增量维护，切分类只是本地过滤。详见 §2、§3。

## 7. 播放与弹幕（这两块结论没变）

- 播放：`rtmp://<域名>/live/<房间号>` / `http://<域名>/live/<房间号>.flv`，**零鉴权**，
  抓包里那串 `?token=…&t=…&liteavToken=…` 去掉照样能拉；`.m3u8` 在同一台 nginx 上也返回 FLV（没做 HLS）。
- 弹幕：WS `/tunnel/open` → `/websock/join` → `/websock/history_msg` → 推送 `ctl=room_msg`。
  帧格式与消息类型码见 `明文长连接通道.md`、`弹幕分类与过滤.md`。
