## 1. 原 app 的做法（为什么我们敢走这条路）

【代码证据】来自 6.24 未混淆版 blutter 产物 `out_dir/asm/`：

| 项 | 事实 |
|---|---|
| 直播播放 | 自研插件，`MethodChannel("LivePlayer")`，方法 `init/play/pause/resume/release/reset/mute/isMute/replay/checkPlayingUrl/addUrlStrs/setInterfaceDirection` |
| 渲染 | `_buildTextureView()` → 外部纹理交给 Flutter |
| 第三方播放器 | **无**（无 vlc/media_kit/fvp/ijk/txplayer/aliplayer） |
| `video_player` | 仅用于聊天短视频，**不是直播** |
| 弹幕 | 纯 Flutter widget（`BarrageView` 双动画轨道），与播放器解耦 |

**关键推论**：原 app 不用 Media3 的 FLV 解析器，所以能播 HEVC；
我们用「自定义 Extractor + Media3」可以拿到等价效果，且比从零写 MediaCodec 管道风险低得多。

## 2. 播放链路设计

```
DataSource(OkHttp/Default) → FlvHevcExtractor → Media3 渲染管线
                                                    ├─ MediaCodec 硬解 HEVC
                                                    ├─ AudioTrack 播 AAC
                                                    └─ SurfaceView（零拷贝）
```

### 2.1 为什么必须自己写 Extractor

【已验证】Media3 源码 `VideoTagPayloadReader`：

```java
private static final int VIDEO_CODEC_AVC = 7;
// Support just H.264 encoded content.
if (videoCodec != VIDEO_CODEC_AVC) {
  throw new UnsupportedFormatException("Video format not supported: " + videoCodec);
}
```

我们的流是 **codecId = 12（HEVC）**，走内置 FlvExtractor 必然抛异常。

### 2.2 FlvHevcExtractor 实现规格

结构照抄 Media3 的 `FlvExtractor`（状态机 + tag 循环），只把 video payload 换成 HEVC 版本：

```
FLV 布局：
  [9B 头: 'FLV' ver flags dataOffset(4)]
  [4B PreviousTagSize0 = 0]
  循环 {
    [11B tag 头: type(1) dataSize(3) timestamp(3+1) streamId(3)]
    [dataSize 字节 tag 数据]
    [4B PreviousTagSize]
  }
  type: 8=audio, 9=video, 18=script
```

**video tag 数据（codecId=12，与 AVC 同构）**：

```
byte0 = (frameType<<4) | 12        # frameType 1=关键帧
byte1 = packetType                 # 0=配置(seq header) 1=NALU 2=end
byte2..4 = compositionTime(ms, 24bit, 有符号)
byte5..  = 负载
```

实现要点：

```kotlin
private const val VIDEO_CODEC_HEVC = 12

// 配置帧
if (packetType == 0 && !hasOutputFormat) {
    val cfg = HevcConfig.parse(data)          // androidx.media3.extractor.HevcConfig
    output.format(Format.Builder()
        .setContainerMimeType(MimeTypes.VIDEO_FLV)
        .setSampleMimeType(MimeTypes.VIDEO_H265)
        .setCodecs(cfg.codecs)
        .setWidth(cfg.width).setHeight(cfg.height)
        .setPixelWidthHeightRatio(cfg.pixelWidthHeightRatio)
        .setInitializationData(cfg.initializationData)
        .build())
    nalUnitLengthFieldLength = cfg.nalUnitLengthFieldLength
    hasOutputFormat = true
    return false
}

// NALU 帧：长度前缀 → 起始码
if (packetType == 1 && hasOutputFormat) {
    val isKey = frameType == 1
    if (!hasOutputKeyframe && !isKey) return false
    // 与 Media3 AVC 实现一致：把 BigEndian 长度前缀替换成 00 00 00 01
    ...
    output.sampleMetadata(timeUs, if (isKey) C.BUFFER_FLAG_KEY_FRAME else 0, bytesWritten, 0, null)
}
```

`HevcConfig.parse()` 已确认存在，返回 `initializationData / width / height / nalUnitLengthFieldLength / codecs`。

**接入方式**：


### 2.3 播放器配置（低延迟、低占用）

```kotlin
val renderers = DefaultRenderersFactory(context)
    .setEnableDecoderFallback(true)                    // 硬解失败自动换下一个
    .setExtensionRendererMode(EXTENSION_RENDERER_MODE_OFF)

val loadControl = DefaultLoadControl.Builder()
    .setBufferDurationsMs(2_000, 12_000, 500, 1_000)   // 直播：小缓冲
    .build()

val player = ExoPlayer.Builder(context, renderers)
    .setLoadControl(loadControl)
    .build()

player.setVideoSurfaceView(surfaceView)                 // ★ 必须 SurfaceView，不要 TextureView
player.setMediaItem(item)
player.prepare()
player.playWhenReady = true
```

- `SurfaceView`：直接合成到 GPU 层，零拷贝；`TextureView` 要多一次纹理上传。
- 直播不需要 seek，`SeekMap.Unseekable` 即可（Extractor 里 `ensureReadyForMediaOutput`）。
- 屏幕常亮：`surfaceView.keepScreenOn = true`。

```
3. 若设备无 HEVC 解码器 → 用服务端 /ts?u=...&q=720（H.264 兜底）
4. 若都失败 → 展示明确错误码（不是白屏）
```

## 3. 接口层：如何应对 token / 接口变化

这是长期可用性的关键，必须一开始就设计成「可远程修正」。

### 3.1 已知的易变项

| 项 | 现状 | 变化风险 |
|---|---|---|
| `auth_key`（流地址内） | 有效期 **300 分钟**【已验证】 | 必然过期，必须定期刷新 |
| `authorization`（登录令牌） | 由用户提供 | 会过期，**无法自动续期**（未见登录接口） |
| `version` | app 433 → 网页 **436** | 服务端可能校验，需可配置 |
| `salt`（签名盐） | `oknzoiwe@23` | 可能变 |
| `ak` | `jyzb` | 可能变 |
| 域名池 | `utp.opuxrcm.com` / `ytt.jvjzmc.com` | 会轮换 |
| 字段名 | app 返回 `pullStreamAddr*`，网页解析 `pullAddress*` | **已出现跨端命名差异** |

### 3.2 三层设计

**第一层：优先走服务端聚合接口**（推荐，屏蔽全部加密细节）

```
GET /api/rooms   →  房间列表（含 playPath、oneToOneState）
GET /health      →  服务是否健康
```

App 端零加密实现。刷新数据由 PC 上的 `启动网页.bat` 完成。

**第二层：App 内自带加密实现**（脱离 PC 时）

按 §3.3 在 Kotlin 里实现「路径混淆 + 签名 + xorCode」，参数全部来自 `RemoteConfig`。

**第三层：远程配置兜底**

```kotlin
data class RemoteConfig(
    val salt: String = "oknzoiwe@23",
    val ak: String = "jyzb",
    val terminal: Int = 3,
    val channel: Int = 12,
    val version: String = "436",
    val hosts: List<String> = listOf("https://utp.opuxrcm.com", "https://ytt.jvjzmc.com"),
    val wsHosts: List<String> = listOf("wss://yzj.opuxrcm.com/live", "wss://zcp.sid1688.com/live"),
    val imKey: String = "t4@*77~i&4j#~#c~",

```

启动时拉一个自己的配置 JSON（或打包内置 + 本地可覆盖）。**改配置就能应对大部分漂移，不用重新发版。**

### 3.3 加密算法（已完全还原，可直接移植）

```
① 路径
token = "/" + prefix + hex_each_char(base64(path))
        prefix = 3 个随机十六进制字符（服务端忽略；长度须为奇数）
        反解：从偏移 0..19 尝试，取能 base64 解出 "/" 开头可打印串的那个

② 签名
d = {ak, authorization, channel, terminal, version, "x-auth-timestamp": ts} ∪ 业务参数
src = path + "?" + "&".join("k=v" for k in sorted(d))     # 按 code unit 升序
x-auth-sign = md5(src + salt)

③ 报文体
xor(s) = chr((ord(c) ^ 0x152E) & 0xFFFF)   # 自逆；响应同样处理
```

Kotlin 注意点：
- `sorted()` 用默认 `String.compareTo`（code unit 序），不要用 `Collator`
- 对象/数组参数用**紧凑 JSON**（无空格），与 Python `separators=(",",":")` 一致
- `xorCode` 结果按 **UTF-8** 编码发送；接收时先 UTF-8 解码再 xor

### 3.4 字段别名容错

```kotlin
fun pickAddress(o: JSONObject, kind: String): String = when (kind) {
    "orig" -> o.optString("pullStreamAddr").ifEmpty { o.optString("pullAddress") }
    "p720" -> o.optString("pullStreamAddr720").ifEmpty { o.optString("pullAddress720") }
    "p360" -> o.optString("pullStreamAddr360").ifEmpty { o.optString("pullAddress360") }
    else -> ""

```

### 3.5 刷新策略

- 房间列表缓存 60 秒；进入房间前若 `auth_key` 剩余 < 5 分钟 → 强制刷新
- 播放 403/断流 → 拉一次新地址重试，最多 2 次
- token 失效（HTTP 500 / code≠0）→ 明确提示「令牌过期，请重新登录/粘贴令牌」，**不要静默重试**
- 域名失败 → 依次切换 hosts 列表

## 4. 弹幕：实现方案（已实测）

### 4.1 【已验证】协议全貌

**连接**（明文 JSON over WSS，无需额外加密）：

```
wss://<webSocketDomain>?auth=<authorization>&s=<毫秒时间戳>&aid=<设备ID>&v=<version>
```

实测：`wss://yzj.opuxrcm.com/live?auth=...&s=...&aid=...&v=436` → `HTTP/1.1 101 Switching Protocols`

**发送帧（明文 JSON）**：

```json
{"type":"1002","toLiveId":"<roomId>"}      // 进房（主播自己进自己的房用 1008）
{"type":"1003","toLiveId":"<roomId>"}      // 退房
{"type":"1007"}                            // 心跳
```

心跳周期由 `Timer.periodic` 驱动；**连续 3 次未收到 pong 即重连**（收到含 `pong` 的帧则计数清零）。

**接收帧**：Base64 文本 → AES 解密 → protobuf

【已验证】解密参数：

| 项 | 值 |
|---|---|
| 算法 | AES-128-**CBC** / PKCS7 |
| 密钥 | `t4@*77~i&4j#~#c~`（16 字节，硬编码） |
| 数据 | `base64decode(去掉首尾引号后的文本)` |
| 明文 | 头部为 protobuf 帧（`08 15 12 <len>` = type 21 进房结果），其内嵌 JSON 字段 |

实测解出的真实业务字段（原文片段）：

```
{"liveId":"2026...","ls":1,"us":1}
{"ses":0,"evt":1,"fm":0,"lv":13,"uIc":"/tx/12.png","uid":"6460...","mid":"8643..."}
{"bet":"10.00","evt":17,"gid":1,"gn":"一分快三","en":"game.name.fast3","betFen":1000,...}
{"ses":1,"evt":1,"ik":"cr_9","cn":"动感摩托","uIc":"/tx/30.png","uid":"8643..."}
```

已识别的字段：
`evt`（事件类型：1=聊天/进场类，17=下注，53=?）、`uid`、`cn`（昵称）、`uIc`（头像）、
`lv`（等级）、`gt`、`ses`、`mid`（消息ID）、`ik`、`bet/betFen/gn`（下注）。

**【待补】两点**：

1. **AES 的 IV 未最终确认**。现象：每次只有**第 1 个 16 字节块**解错（CBC 特性），第 2 块起完全正确
   → 密钥正确、IV 错误。已用「已知明文反推」得到强候选 `B\x01Z\x1avt3(jd8|97no`（6/6 帧首字节校验通过），
   但进房帧的 protobuf 长度前缀还需精确到字节，才能 100% 定死。
2. **protobuf schema**：需要从 `im/bean/*`（生成代码）反推字段号，或直接用「跳过首块 + 正则提取 JSON 字段」的兼容做法。

### 4.2 建议实施顺序

| 步骤 | 做法 | 产出 |
|---|---|---|
| ① 连接 | OkHttp `newWebSocket`，按上面 URL 拼接 | 能收到帧 |
| ② 解密 | AES-128-CBC + 已知密钥；**先固定 IV 候选**，用下面的自检脚本定死 | 拿到明文 |
| ③ 解析 | 两种都实现，取成功的那个：<br>a) protobuf（推荐，最稳）<br>b) 正则从可读尾部提取 `evt/uid/cn/uIc/lv` | 得到结构体 |
| ④ 渲染 | DanmakuView（见 §4.3） | 滚动弹幕 |

**自检脚本**（Python，用于定 IV，已验证可跑通）：

```python
KEY = b"t4@*77~i&4j#~#c~"
pt = AES.new(KEY, AES.MODE_CBC, IV).decrypt(base64decode(frame))
# 正确 IV 的判据：pt[0]==0x08 且 pt[1]==0x15（type=21 进房帧）
#              且 pt[2]==0x12 且 pt[3] 为 JSON 长度，其后紧接 '{"liveId"'
```

### 4.3 高性能 DanmakuView

```kotlin
class DanmakuView(ctx: Context) : View(ctx) {
    private val pool = ArrayDeque<Item>()          // 对象池，避免 GC
    private val active = ArrayList<Item>(64)
    private val paint = Paint(Paint.ANTI_ALIAS_FLAG).apply { textSize = 14f * density }
    private var lastFrameNs = 0L

    private val frameCb = Choreographer.FrameCallback { ns ->
        val dt = if (lastFrameNs == 0L) 0f else (ns - lastFrameNs) / 1e9f
        lastFrameNs = ns
        step(dt)                                    // 只算位置，不分配对象
        invalidate()
        Choreographer.getInstance().postFrameCallback(this)
    }
    // onDraw 里只做 drawText，按 track 计算 y；不做 measure、不 new 对象
}
```

要点：
- **Choreographer 驱动**，不用 `ValueAnimator`/`Handler`
- 文本宽度在**入池时**用 `paint.measureText` 算一次并缓存
- 轨道数固定（如 6 条），满了就丢弃最旧的一条
- `onDraw` 内**零分配**：不拼字符串（`cn + ": " + text` 在入池时拼好）
- 图层：`setLayerType(LAYER_TYPE_HARDWARE, null)`
- 上限保护：同时在屏 ≤ 60 条

### 4.4 弹幕降级

若 §4.2 的 ②③ 短期无法完成，仍可交付：
- 用「跳过首块 + 正则提取」先做出**只读弹幕**（能显示昵称+内容）
- 或先只做聊天列表（右侧 IM 消息流），不做飞行弹幕
- **不要**为了弹幕拖住播放功能上线

## 9. 风险与硬约束

1. **HEVC 硬解依赖设备**：极老机型无 HEVC 解码器 → 走 `/ts` H.264 兜底（需服务端在线）。
2. **token 必须人工提供**：未发现登录接口，无法自动续期。
3. **`auth_key` 300 分钟**：必须定期刷新房间列表。
4. **弹幕 IV/schema 未 100% 闭环**：见 §4.1 的【待补】，但已有可用的降级路径。
5. **接口可能整体改版**：`version` 已从 433 走到 436；改版后需重新逆向，§3.2 的远程配置能覆盖一部分。
6. **`-c copy` 转封装不可用**：实测 FLV→TS 直拷只有 6–38 KB/s 且 SPS 丢失，**不要再尝试这条路**。

```
→ {"code":0,"data":{

     "pullAddress":    "https://pl.ycscts.com/h001/<id>_eh5.flv?auth_key=...",
     "pullAddress360": "https://pl.ycscts.com/h001/<id>_b1.flv?auth_key=...",
     "pullAddress720": "https://pl.ycscts.com/h001/<id>_b3.flv?auth_key=..."
   }}
```

实测返回的地址与列表接口的 `pullStreamAddr*` **完全同源同格式**（`_eh5/_b1/_b3`）。

**两套字段名并存，必须都兼容：**

| 来源 | 字段 |
|---|---|
| `/home/default/cls/query`（列表） | `pullStreamAddr` / `pullStreamAddr360` / `pullStreamAddr720` |
| `/app/live/joinRoom`（进房） | `pullAddress` / `pullAddress360` / `pullAddress720` |

旧版 app 用的是 `pullStreamAddr*`，最新网页用的是 `pullAddress*`——这正是「以网页为准」的差异点。

### 10.2 网页是怎么播 HEVC 的【已验证】

网页首屏加载的脚本里有：

```html
<script src="./jessibuca_v3.3.21.js"></script>
```

**Jessibuca 是 WASM 软解码播放器**，支持 HTTP-FLV / WebSocket-FLV 的 H.264 **和 H.265**。
这就解释了「浏览器 MSE 不支持 HEVC，但网页能播」——它根本不走 MSE，而是用 WASM 自己解。

对我们的意义：

| | 网页 | 我们的原生 App |
|---|---|---|
| HEVC 解码 | WASM **软解**（吃 CPU、耗电、高发热） | **MediaCodec 硬解**（专用解码单元） |
| 功耗 | 高 | 低 |
| 同屏多路 | 很难 | 可行 |

**结论：原生 App 走硬解，性能明显优于网页版，方向正确。**

### 10.3 不存在 H.264 / m3u8 备用源【已验证】

- 换 `.m3u8` / `.ts` 后缀 → 403（`auth_key` 与路径绑定）
- `m3u8InterfaceDomain`（`hjm.aynjxxw.com`）→ 400/空体
- `hk/zb.yfhx.live`、`aes.piwb.live` → 404/400
- `/app/live/joinRoom` 返回的仍是 `_eh5.flv`（HEVC）

**不要指望找到 H.264 源**。要 H.264 只能自己转码，而转码会掉画质、吃 CPU。
所以「自定义 FLV/HEVC 提取器 + 硬解」是本项目唯一的高质量路线。

### 10.4 对 §3 接口层的修订

- `RemoteConfig` 的 `version` 默认值应为 **436**、`terminal=3`、`channel=12`（网页口径）
- 播放前**先调 `/app/live/joinRoom`** 取地址；列表里的地址仅用于展示/预热
- 别名解析需同时覆盖 `pullAddress*` 与 `pullStreamAddr*`
- `/room/staticData/live` 只有房间静态信息（无播放地址），不要指望它
- `/oneToOne/getStatus` 传 `{"liveId": ...}`，`status=0` 表示正在表演
