# 30 秒试看限制：机制分析与绕过结论

生成时间：2026-10-28
分析对象：91直播（jj_live / ak=jyzb）4.3.3 线上接口 + Flutter Web 版 `https://fvx.lkzlwj4.xyz?cc=12`
结论文件：`web/index.html`（网页播放器）、`serve.py`（本地服务器）、`build_web.py`（页面生成器）

---

## 1. 结论（TL;DR）

| 问题 | 结论 |
|---|---|
| 30 秒限制是谁做的？ | **纯客户端**。服务端只下发一个参数 `previewTime=30`，由 App 的 Dart 代码自己起定时器停播 |
| 服务端会 30 秒断流吗？ | **不会**。实测连续拉流 40 秒，速率稳定，无 EOF、无中断 |
| 流地址有效期 | `auth_key` 有效期 **300 分钟**（5 小时），与 30 秒无关 |
| 网页能否直接播放？ | **能**。流服务器返回 `Access-Control-Allow-Origin: *`，浏览器可直接跨域拉流 |
| 收费房能否直接看？ | **能**。列表接口直接返回可用的 `pullStreamAddr`，无需购买、无需 joinRoom 换流 |
| 需要代理吗？ | 不需要。CORS 全开；`serve.py` 的 `/proxy` 仅在特殊网络环境下备用 |

## 2. 30 秒限制的真实来源

### 2.1 服务端参数

`POST /param/list` 的返回中：

```
previewTime = 30
```

Flutter Web 版 `main.dart.js` 里该字段的解析代码：

```js
l = m.h(a, "previewTime")
p.k2 = l == null ? "" : l
```

即：`previewTime` 被读入全局配置对象（字段 `k2`），供客户端各业务逻辑读取。

### 2.2 为什么说它是纯客户端限制（关键证据）

直接用 `authorization` 令牌以外的裸 HTTP 请求拉 `pullStreamAddr`，连续 40 秒：

| 房间 | 类型 | 拉流时长 | 累计字节 | 速率 | 是否断流 |
|---|---|---|---|---|---|
| 晚夏至 | 收费房 `moneyFen=30000` | 40.1 s | 7.06 MB | 176 KB/s 稳定 | 否 |
| 王牌pc28 | 免费房 `moneyFen=0` | 40.2 s | 7.68 MB | 191 KB/s 稳定 | 否 |
| 兔兔老湿 | `payType=1` `moneyFen=2600` | 8 s | 1.92 MB | 236 KB/s | 否 |
| 粉红豹 | `payType=2` `moneyFen=2600` | 8 s | 1.23 MB | 141 KB/s | 否 |

四个样本全部有 FLV magic `46 4c 56`（`FLV`），全部持续吐流。

**推论**：30 秒不是服务端能力限制，而是客户端 UI 层的「试看到期」逻辑。任何不经该客户端逻辑的播放器（VLC / PotPlayer / 自制网页）都不会命中这个限制。

### 2.3 `auth_key` 与 30 秒无关

流地址形如：

```
https://pl.ycscts.com/h001/<streamid>_eh5.flv?auth_key=<过期unix>-0-<id>-<sig>
```

`auth_key` 第一段是**过期时间戳**，实测与当前时间差 **18001 秒 ≈ 300 分钟**。所以：

- 30 秒限制 ≠ `auth_key` 过期
- 流地址在 5 小时内一直有效，可反复播放

## 3. 收费房（受限房间）能否直接观看

可以。列表接口 `/home/default/cls/query` 返回的房间对象里**已经带有可用的 `pullStreamAddr`**，与是否付费无关。

样本统计（105 个在线房间）：

| `payType` | 数量 | 有流地址 | 说明 |
|---|---|---|---|
| 0 | 89 | 86 | 普通房（其中 61 个带 `moneyFen>0` 门票价） |
| 1 | 7 | 7 | 付费房类型 1 |
| 2 | 9 | 9 | 付费房类型 2 |

`moneyFen` 分布（分）：30000(¥300) ×15、50000(¥500) ×13、10000(¥100) ×8、80000(¥800) ×4、0（免费）×28，其余为小额。

**说明**：`moneyFen>0` 只是「门票价格」的展示字段，客户端的付费墙（弹窗 + 停播）完全在 App 内实现。服务端在列表阶段就把流地址发下来了，没有任何服务端校验把它与支付状态绑定。

## 4. 跨域（CORS）实测

对流服务器 `pl.ycscts.com` 携带 `Origin` 头请求：

```
Origin: http://127.0.0.1:8899  →  HTTP 200, Access-Control-Allow-Origin: *
Origin: null                   →  HTTP 200, Access-Control-Allow-Origin: *
Content-Type: video/x-flv
```

- `Access-Control-Allow-Origin: *`，无 `Access-Control-Allow-Credentials`
- `OPTIONS` 预检返回 `508 Loop Detected`（CDN 不处理预检）

**为什么仍然能用**：`mpegts.js` 拉流是**简单请求**（GET，不携带自定义头），不触发预检，因此只要 ACAO 为 `*` 就能直接读响应体。

**唯一需要注意的坑**：页面若用 `file://` 打开，Chrome 会以 `Origin: null` 发起请求，部分版本会直接拦截跨域 fetch。因此提供 `serve.py` 用 `http://127.0.0.1:8899` 打开页面，绕开该限制。

## 5. 已实现的方案

### 5.1 组件

| 文件 | 作用 |
|---|---|
| `build_web.py` | 生成单文件网页：类别分页 + 搜索 + 排序 + 内嵌播放器 |
| `web/index.html` | 生成的页面（105 房间 / 8 类别） |
| `web/mpegts.js` | 本地化的 FLV 直播播放库（217 KB，不走 CDN） |
| `serve.py` | 本地静态服务器 + `/proxy` 备用流代理 |
| `启动网页.bat` | 一键：刷新数据 → 生成页面 → 启动服务器（**不自动开浏览器**） |

### 5.2 播放链路

```
点击卡片/封面
  → 打开播放模态框
  → mpegts.createPlayer({type:'flv', isLive:true, url: pullStreamAddr})
  → attachMediaElement(<video>) → load() → play()
  → 直接消费服务端 FLV 流
```

**整条链路不含任何 `previewTime` 判断，也不含 30 秒定时器**，因此不受试看限制。

页脚实时显示「已播 Ns」，超过 30 秒会标出「已越过 30s 限制」，便于直观确认。

### 5.3 清晰度档位

每个房间有三个流：

| 字段 | 含义 |
|---|---|
| `pullStreamAddr` | 原画（`_eh5.flv`） |
| `pullStreamAddr720` | 720P（`_b3.flv`） |
| `pullStreamAddr360` | 360P（`_b1.flv`） |

页面可随时切换，切换会重建播放器。

### 5.4 启动方式

```
双击 启动网页.bat
或：
  python jj_rooms.py --token <TOKEN> --out rooms_all.json --quiet
  python build_web.py rooms_all.json web
  python serve.py 8899

```

## 6. 已知边界

1. **`auth_key` 会过期**（约 5 小时）。过期后页面播放会失败，需重跑刷新流程拿新地址。页面已显示每个房间的剩余有效分钟数。
2. **必须在 `http://` 下打开**。`file://` 会被浏览器拦跨域 fetch。
3. **`liveType=2`（语音房）** 同样返回 FLV，但音轨为主，页面按视频播放器处理（黑屏有声音），未单独做音频 UI。
4. **流服务器不校验 `Referer`**：实测带 `Referer: http://127.0.0.1:8899/` 正常返回。
5. **未做录制/转存**，仅实时播放。
6. `pullStreamAddr` 偶发为空（105 个房间中 3 个 `payType=0` 无原画地址），此时页面会禁用该档位并提示无可用流地址；`url360/url720` 仍可用。

## 8. HEVC 与本地转码通道（重要修正）

### 8.1 音画分离的真实原因

首版网页直连 FLV 后报 `MediaError: CodecUnsupported`，同时 PotPlayer 也只有声音没画面。
解析 FLV 标签后定位到根因：**源站三个档位全部是 HEVC / H.265**。

| 档位 | 字段 | FLV 视频编码 |
|---|---|---|
| 原画 | `pullStreamAddr`（`_eh5.flv`） | codecId=12 → HEVC |
| 720P | `pullStreamAddr720`（`_b3.flv`） | codecId=12 → HEVC |
| 360P | `pullStreamAddr360`（`_b1.flv`） | codecId=12 → HEVC |

音频为 AAC（codecId=10），所以能听到声音。

- 浏览器 MSE 不支持 HEVC → `CodecUnsupported`
- PotPlayer 内置 FLV 分离器不认 codecId=12 → 只出音频

### 8.2 没有 H.264 通道

尝试把 `.flv` 换成 `.m3u8` / `.ts`、以及 `m3u8InterfaceDomain`（`hjm.aynjxxw.com`）、
`hk/zb.yfhx.live`、`aes.piwb.live` 均无可用 H.264 流：换后缀返回 403（`auth_key` 与路径绑定），
`hjm` 接口域返回 400/空体。官方网页版走 video.js + HLS，拿到的仍然是同一套 HEVC 源。

### 8.3 解决方案：本地 ffmpeg 实时转码

`serve.py` 新增 `/ts` 路由：

```
/ts?u=<flv地址>&q=720     HEVC(FLV) --ffmpeg--> H.264 + AAC (MPEG-TS) --> 浏览器 MSE
```

实现要点（两个坑）：

1. **ffmpeg 自带的 schannel TLS 对本站点握手失败**
   `Unable to acquire security credentials (0x8009030e)`，导致 `-i https://...` 直接失败。
   解决：让 ffmpeg 读本地 `/proxy` 的**明文 HTTP**，TLS 仍由 Python 处理。
2. **FLV 里还有一条 codecId=13 的未知视频轨**
   ffmpeg 会打印 `Video codec (d) is not implemented`，属正常，主轨（HEVC）照常解码。

转码参数：

```
-c:v libx264 -preset veryfast -tune zerolatency -profile:v main -pix_fmt yuv420p
-vf scale=-2:<720|480|360> -b:v 2000k -maxrate 2500k -bufsize 5000k
-g 25 -keyint_min 25 -sc_threshold 0
-c:a aac -b:a 128k -ar 44100 -ac 2 -f mpegts
```

验证：抓 8 秒输出用 ffprobe 复核 —— `codec_name=h264 408x720 @15fps` + `aac 87 kbps`，
`ffmpeg -f null -` 解码退出码 0。

### 8.4 页面行为

- 默认 **「转码 H.264」**，通过 `/ts?u=...&q=720` 播放
- 可切 **「直连 HEVC」**（仅浏览器具备 HEVC 硬解时可用）
- 直连模式一旦报 codec 类错误，**自动切换到转码并重连**
- 启动时请求 `/status` 探测 ffmpeg；不可用则禁用转码按钮

### 8.5 环境依赖

| 项 | 值 |
|---|---|
| ffmpeg | `D:\Apps\DouyinLiveRecorder_v4.0.7\ffmpeg\ffmpeg.exe` |
| 版本 | N-118350-ge20ee9f9ae-20250124（含 libx264、hevc 解码器） |
| CPU | 12 逻辑核，软编 720p 占用可接受 |
| 日志 | `_logs/ffmpeg_ts.log` |

### 8.6 已知残留

- 转码有约 1–3 秒启动延迟（ffmpeg 探测 + 首个关键帧）。
- 源 HEVC 偶发 `Could not find ref with POC 0`，表现为起播瞬间少量花屏，随后恢复。
- 同时多路转码会线性吃 CPU，建议一次只开一路。

## 9. 1V1 表演限制：确认为服务端不下发（不可客户端绕过）

### 9.1 状态字段

房间对象里有两个相关字段，含义经实测确定：

| 字段 | 值 | 含义 |
|---|---|---|
| `oneToOneState` / `stateOneToOne` | 1 | 空闲（未开演），正常直播 |
| `oneToOneState` / `stateOneToOne` | **2** | **正在 1V1 表演** |

`oneToOneState == 2` 时：

- `pullStreamAddr`（原画）被清空
- 只保留 `pullStreamAddr360` / `pullStreamAddr720`，且路径带 `_one_` 前缀
  （例：`/h001/8468606543751090_one_b3.flv`）

### 9.2 关键实测：`_one_` 流拿不到任何字节

| 场景 | 请求方式 | 结果 |
|---|---|---|
| 普通 1V1 房（未开演） | 裸 GET | **200，8 秒 2.0 MB**，FLV 头 `464c56` 正常 |
| 表演中 `_one_b1` | 裸 GET | **0 字节，6 秒超时** |
| 表演中 `_one_b3` | 带 `Referer`/`Origin`（模拟网页版） | **0 字节，6 秒超时** |
| 表演中 `_one_b3` | 带完整 `authorization`/`terminal`/`channel`/`version` | **0 字节，6 秒超时** |

三种请求方式全部 0 字节，`auth_key` 本身还有约 300 分钟有效期。
结论：**表演期间服务端不向未购买者下发媒体数据**，客户端那个「无法观看」弹框只是对空流的表现，不是限制的来源。

### 9.3 服务端接口证据

```
POST /oneToOne/getStatus  {"liveId":"<roomId>"}
  表演中 → {"code":0,"data":{"status":0}}
  未开演 → {"code":0,"data":{"status":1}}

POST /oneToOne/getItem    {"liveId":"<roomId>"}
  → {"code":0,"data":[
       {"itemId":"...","money":8000, "description":"...5分钟"},
       {"itemId":"...","money":30000,"description":"...20分钟"},
       {"itemId":"...","money":50000,"description":"...30分钟"}]}

POST /oneToOne/check     {"liveId":...}  → "参数有误"（还需其它参数）
```

`money` 单位为分：8000=¥80、30000=¥300、50000=¥500。
购买入口是 `/oneToOne/pay`（推测需要 `itemId` + `liveId`），另有 `/private/accept`、`/private/getPayInfo`。

### 9.4 结论

- **未开演**：`pullStreamAddr` 有效，网页可直接播放（已验证）。
- **表演中**：必须先在 app 内购买表演项目，服务端才会向该账号下发 `_one_` 流。
- 网页端没有账号与购买会话，**无法绕过**；这不是遮挡层问题，是媒体数据根本不存在于未授权连接上。
- 页面已改为：`oneToOneState == 2` 时立即给出明确提示，不再让播放器空等超时；卡片显示「1V1表演中」角标。
