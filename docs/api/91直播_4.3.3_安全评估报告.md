## 1. 结论速览

**没有发现"教科书式后门"**——即：无短信收发/读取、无通讯录读取、无无障碍（Accessibility）服务劫持、无通知监听、无隐藏 dex/APK 动态载荷、无内嵌二次安装包、无自建 native C2、无静默安装。

**但总体风险等级：高。** 原因是它把"可远程控制的高危能力"组合齐了，且自身完整性与来源不可信：

| 维度 | 判定 |
|---|---|
| 传统后门（盗号/远控/静默装马） | 未发现 |
| 再打包/换皮痕迹 | **确认存在**（NP管理器字符串加密 + manifest 混淆 + zip 伪条目 + 公开 debug 证书） |
| 远程投递能力（推送安装 APK） | **具备**（OTA 升级链路 + REQUEST_INSTALL_PACKAGES） |
| 卸载其它应用能力 | **具备**（REQUEST_DELETE_PACKAGES + `uninstallOldPkg`，包名由 Dart 层/配置传入） |
| WebView 越权桥 | **存在且无来源校验**（`app_util` 任意 GET/POST + Cookie 读写） |
| 支付页面自动化 | **存在**（`cardPayWrap` 自动点击最后一个支付通道） |
| 域名动态下发/抗封切换 | **存在**（GitHub / RAP2 / 腾讯 COS / EdgeOne 函数多通道） |
| 传输安全 | `cleartextTrafficPermitted=true`，全域允许明文 HTTP，无证书固定 |
| 数据外发 | Sentry 双 DSN 上报崩溃/性能/设备上下文；Simonsdk 归因上报 |

一句话：**它不像"被植入了木马"，它本身就按"可远程改控的灰产客户端"设计**；真正需要担心的不是"有没有后门"，而是"控制它的人能在你机器上做哪些事"。

## 2. 关键证据

### 2.1 反分析 / 重打包痕迹（确认存在）

1. **AndroidManifest.xml 被故意做成非法 XML**
   apktool 直接报 `元素类型 "manifest" 必须后跟属性规范 android:versionCode`、`前缀 android 未绑定`、`Skipping unexpected RES_TABLE_PACKAGE_TYPE chunk`。
   自写 AXML 解析显示：每个真实标签后面都插了一条 `android:name="false"` 的伪属性记录，`<manifest>` 被拆成两段（`package="…"` 被塞到 `</manifest>` 之后）。
   证据：`_audit\manifest_dump.txt:1-10`

2. **zip 里塞了 96 个"影条目"与 49 个重名条目（zip 覆盖攻击手法）**
   形如 `/AndroidManifest.xml/  .9.png`、`classes.dex////.webp`、带反斜杠与引号的路径，使 tar/资源管理器解包时把真文件变成目录、或让不同工具读到不同内容。
   证据：`_audit\entries.txt`、`_audit\shadow\`

3. **字符串全量加密（NP管理器 StringFog）**
   `Lobfuse/NPStringFog;->decode()`，密钥 `npmanager`：hex → 逐字节 XOR → `$-sxg-$` 还原为 `\`。
   全包 1422 处调用、711 条唯一明文（多为 SDK 权限名/协议串）。这是"用 NP 管理器一键加固/汉化/去广告"的典型指纹。
   证据：`_audit\apt\smali\obfuse\NPStringFog.smali`、`_audit\npf_unique.txt`

4. **用公开的 Android 调试私钥签名**
   任何拿到 androiddebugkey 的人都能签出"同一个签名"的替换包；正常商业发行不会这么做。结合 1–3，可判定该 APK 是**第三方重打包产物**，而非官方原包。

5. 其他残留：`assets/simon` = `{"version": "2.8.2"}`；`META-INF` 里塞了 `spring.factories`、`kotlinx_coroutines_core.version` 等无关文件；测试地址 `http://10.10.20.131:9999`、`http://rap2api.taobao.org` 未清理。

### 2.2 WebView JS 桥 `app_util`（最值得注意的设计缺陷）

`JDRechargeActivity` 用 `MyJavaScriptInterface$Companion.config()` 给 WebView 打开：JS、DOM Storage、Geolocation、`setAllowFileAccess(true)`、`setCacheMode(2)`，并注入 `addJavascriptInterface(bridge, "app_util")`，随后加载**服务端下发的充值 URL**（`rechargeByJD(recharge_url)`）。

桥暴露的方法（全部无来源校验、无域名白名单）：

| 方法 | 能力 |
|---|---|
| `Get(url, headers, cookie)` | 用 App 进程身份发起**任意 GET**，可带任意 Header / Cookie，返回响应体给 JS |
| `Post(url, body, headers, cookie)` | 同上，**任意 POST** |
| `loadUrl(url)` | 让 WebView 跳任意地址 |
| `setCookie(domain, ck)` / `removeAllCookie()` | 任意域写/清 Cookie |
| `setUserAgent(ua)` | 改 UA |

证据：
- `_audit\apt\smali_classes16\com\jj\live\audience\MyJavaScriptInterface.smali:148`（Get）、`:330`（Post）、`:546`（loadUrl）、`:626`（setCookie）
- `_audit\apt\smali_classes16\com\jj\live\audience\MyJavaScriptInterface$Companion.smali`（config + `addJavascriptInterface`，接口名 `app_util`）

**含义**：桥被挂到 `JDRechargeActivity` 的 WebView 上，而这个 WebView 加载的是**业务/服务端传入的 `recharge_url`**（`NativeBridgePlugin.rechargeByJD(recharge_url)`），桥本身**不做任何来源校验、不设域名白名单、不区分主框架与 iframe**。也就是说：`recharge_url` 指向/跳转到哪个页面，那个页面就拥有"用 App 身份发任意请求 + 读写 Cookie"的能力（跨域读取 = 绕过同源策略）。当前唯一调用点只有这个充值 Activity（`grep Companion;->config` 仅 2 处：定义与 `JDRechargeActivity.smali:148`）。
另外 `shouldOverrideUrlLoading` 对**不是以 `http` 开头**的 URL 一律 `ACTION_VIEW` 外抛（即 `weixin://`、`alipays://`、`intent://` 等任意 scheme 都能被页面拉起外部应用）。

### 2.3 支付页自动化（`cardPayWrap` 自动点击）

`onPageFinished` 里固定注入：

```js
var cardPayWrapElements=document.getElementsByClassName('cardPayWrap');
for(var i=0;i<cardPayWrapElements.length;i++){
  if(i !== cardPayWrapElements.length-1){ cardPayWrapElements[i].style.display='none'; }
  else { cardPayWrapElements[i].click(); }
}
```

即：隐藏其它支付方式，**自动点最后一个支付通道**。

注入是有条件的（值得如实说明）：`onPageFinished` 里先判断 `url.startsWith("https://mpay.m.jd.com/mpay.")`（该常量同样是 NPStringFog 加密的，解密后为 `https://mpay.m.jd.com/mpay.`）才注入。所以它不会污染任意页面；但"自动选择支付通道"这件事本身写在客户端里，属于支付页自动化操作。
证据：`_audit\apt\smali_classes16\com\jj\live\audience\MyJavaScriptInterface$Companion$config$1.smali`（onPageFinished）

配套的充值域名：`https://mpay.m.jd.com/mpay.`（解密自 NPStringFog，见 `_audit\npf_unique.txt`）。
这属于"支付通道劫持/静默选择"的实现方式：用户看到的选项与实际走账通道不一致。

### 2.9 HuiOne 支付通道（灰产支付，补充判断）

`com.jj.live.flutter.plugin.huione.HuiOneFlutterPlugin`（通道 `jj.live.plugins.huiOne`，深链 `huionetoonelive`——与 MainActivity 的 scheme 完全对应）暴露两个方法：

| 方法 | 行为 |
|---|---|
| `getSignPkgName` | 返回 `包名 - MD5(APK签名)`，即把本机签名指纹交给支付服务端做"防篡改/防马甲"校验 |

**HuiOne Pay 是柬埔寨那家被多国执法点名、与电诈/网赌深度绑定的支付通道**。把它作为内嵌支付方式，本身就坐实了"灰产客户端"的性质。

## 3. 攻击场景推演（"威胁"具体长什么样）

1. **中间人 → 换后端**
   公共 WiFi / 恶意热点 → 劫持域名表下发通道（`http://rap2api.taobao.org` 是明文）或直接对明文接口注入 → App 主 API 指向攻击者服务器。此后所有"服务端下发"的东西都归攻击者：包括充值时传给 `rechargeByJD` 的 `recharge_url` ——该 URL 会在带 `app_util` 桥的 WebView 里打开，于是攻击者页面可以借 App 身份发任意请求、读响应、写 Cookie。
2. **支付通道替换**
   `cardPayWrap` 自动点击"最后一个通道"是硬编码逻辑；一旦充值页被换成攻击者页面，可把用户引导到任意收款方。
3. **更新通道投毒**
   OTA 链路 + `REQUEST_INSTALL_PACKAGES`：谁控制版本接口，谁就能让用户安装任意 APK（签名变了会提示"签名不一致"，但首次安装/换机安装没有这层保护）。
4. **任意应用卸载骚扰**
   `uninstallOldPkg` 的包名列表若改为远端下发，可对指定应用弹卸载框（配合话术即可完成"清理竞品"）。
5. **公开调试签名 → 替换包**
   任何第三方都能用同一 debug 证书签出"同签名"的新包；对已安装用户，系统会当作同一应用升级。

## 4. 处置建议

**普通用户**
1. 不建议安装。若已安装：先断网 → 设置里撤销"所有文件访问/存储"权限 → 关闭"未知来源安装" → 卸载；随后检查是否被静默装了其它应用（设置→应用列表按安装时间排序）、检查是否被加入设备管理器/无障碍。
2. 该应用关联账号若与其它平台同密码，改密码；不要在应用内做实名/绑卡/上传证件。

**开发/运维方（如果这是你们自己的包）**
1. 修 manifest：去掉 AXML 伪属性记录，用标准 aapt2 构建，恢复可校验性。
2. 换正式签名（RSA/EC 私钥），启用 v2+v3，禁止 debug key。
3. `network_security_config`：`cleartextTrafficPermitted="false"`，对 API/支付域加 `<pin-set>`。
4. JS 桥：删掉 `Get/Post`（改由 Dart 侧统一走 Dio），或至少加域名白名单 + 只在 `https://` + 校验来源 URL + 不传 Cookie。
5. 去掉 `cardPayWrap` 自动点击逻辑。
6. 下线 `rap2api.taobao.org` / GitHub README 域名通道，改签名校验的配置接口（HTTPS + 配置签名）。
7. OTA：校验下载包签名与 `versionCode` 单调递增，禁止降级。
8. `MANAGE_EXTERNAL_STORAGE` 改分区存储；`BDService` 加 `exported=false` 或自定义 signature 级权限。
9. 移除测试地址 `10.10.20.131:9999`、`10.0.2.2:8969`、`rap2api.taobao.org`。
