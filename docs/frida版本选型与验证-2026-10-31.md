# frida 版本选型与验证 — 2026-10-31

> 结论先行：**frida 不是版本越高越好。本项目锁定 16.5.9，三端（设备 / PC 两个 Python）版本必须一致。**

## 一、为什么放弃 17.5.0

前几轮反复出现的 `TransportError: timeout was reached`、以及"极简 attach 能过、复杂脚本一加载就卡住"的现象，
一度被归因为 KernelSU 环境下注入不稳定。降级后复测，真正原因有两个：

### 1. JS API 被移除（决定性）

frida 17 移除了 `Module.findExportByName`，改名为 `Module.getGlobalExportByName`。

而仓库里的抓包脚本恰好全用它：

| 文件 | 用到的 API |
|---|---|
| `tools/frida_net_capture.py` | `Module.findExportByName('libc.so','connect'/'send'/'sendto'/'write')` |
| `tools/frida_net_hook.py` | 同上 |

在 17.5.0 下这些调用直接抛异常。异常发生在 `script.load()` 阶段，客户端侧表现为"脚本迟迟不返回 → 超时"，
看起来极像注入失败，实际是脚本自身报错。**这是之前所有"attach 不稳"误判的主因。**

### 2. agent 加载强校验 SELinux 域

17.x 的 agent loader 会校验 SELinux 域，不匹配时直接 `abort()`：

```
agent.vala:411: Oops, SELinux rule probably missing for your system. Symptom: Timeout was reached
```

设备是 KernelSU，adb shell 落在 `u:r:ksu:s0`。域不匹配触发 abort，还会连累 zygote（曾造成"App 全挂"）。

## 二、版本选型依据

| 候选 | 判断 |
|---|---|
| 17.25 / 17.5 | 有上述两个问题，排除 |
| **16.5.9** ✅ | 16.x 末版；兼容 Android 15 / SDK 35；`findExportByName` 仍在；agent 加载宽容；Android 14/15 社区验证最多 |
| 16.2.x / 16.1.x | 更老，Android 15 适配弱于 16.5.x |
| 15.x | 过旧，不支持 Android 15 的部分特性 |

设备环境：OPPO PGZ110，Android 15（SDK 35），arm64-v8a，KernelSU 4.2.0-rc1 + Zygisk + LSPosed。

## 三、三端版本一致性（必须）

frida client 与 server 版本必须匹配，否则握手失败。

| 位置 | 路径 | 版本 |
|---|---|---|
| 设备 | `/data/local/tmp/frida-server` | 16.5.9 |
| Scoop Python | `/d/Apps/Scoop/apps/python/current/python.exe` + `Scripts/frida.exe` | 16.5.9 / frida-tools 13.7.1 |
| WorkBuddy 内置 Python | 用户 site-packages | 16.5.9 |

回滚备份：`/data/local/tmp/frida-server.17.5.0.bak`（52MB，勿删）。

## 四、可复现步骤

### 1. 取二进制

GitHub 直连不通，走镜像：

```bash
curl -L -o frida-server-16.5.9-android-arm64.xz \
  "https://gh-proxy.com/https://github.com/frida/frida/releases/download/16.5.9/frida-server-16.5.9-android-arm64.xz"
```

备用镜像：`ghproxy.net`、`hk.gh-proxy.com`（`ghfast.top` 不通）。

系统没有 `xz` 命令，用 Python 解：

```bash
python -c "import lzma,shutil;open('frida-server-16.5.9-android-arm64','wb').write(lzma.open('frida-server-16.5.9-android-arm64.xz','rb').read())"
```

解压后应为 56,549,232 字节，MD5 `b7a6a4420fe7403fd773397a09d6aec7`。

### 2. 装 PC 端

```bash
# 注意：默认 index 配置会报 "from versions: none"，必须显式指定源
pip install -i https://mirrors.aliyun.com/pypi/simple "frida==16.5.9" "frida-tools==13.7.1"
```

`frida-tools` 必须一起降到 13.x，否则 14.5.2 要求 `frida>=17.5.0` 冲突。

### 3. 替换设备端

```bash
export MSYS_NO_PATHCONV=1
adb push frida-server-16.5.9-android-arm64 /data/local/tmp/frida-server-16.5.9
adb shell "chmod 755 /data/local/tmp/frida-server-16.5.9"
adb shell "/data/local/tmp/frida-server-16.5.9 --version"   # 先验证新文件能跑
# 验证通过后再换名，原文件保留为备份
adb shell "mv /data/local/tmp/frida-server /data/local/tmp/frida-server.17.5.0.bak"
adb shell "mv /data/local/tmp/frida-server-16.5.9 /data/local/tmp/frida-server"
```

### 4. 启动（关键是重定向 fd）

```bash
adb shell "/data/local/tmp/frida-server -D < /dev/null > /data/local/tmp/frida16.log 2>&1"
```

**坑**：不加 `< /dev/null > log 2>&1` 时，daemon 子进程继承 adb 的 stdout，`adb shell` 永不返回，整条命令挂死
（表现为 Bash 调用超时被杀）。加了重定向立即返回。

### 5. 连接

```bash
adb forward tcp:27042 tcp:27042
frida-ps -H 127.0.0.1:27042
```

**坑**：每调用一次 adb，adb server 可能重启，**所有 forward 立即失效**。
所以"建 forward"和"用 frida"必须在同一次命令里完成，或由脚本内部自己 `subprocess` 建 forward
（`tools/frida_attach_test.py` 就是这么做的）。

## 五、实测验证结果

### attach + 读模块（`tools/frida_attach_test.py`）

```
[*] target pid = 16020
[+] attach ok in 0.64s
[+] script loaded in 0.30s
[+] arch=arm64 ptr=8 threads=170
[+] libc: connect=0x71c82c87e0 send=0x71c82e04f0 write=0x71c8334950
    libc.so      @0x71c8235000 size=0x130000
    libflutter.so@0x6feb8ed000 size=0xacb000
    libapp.so    @0x6fe3207000 size=0x19f1000
    libkiwi.so   @0x6fb2257000 size=0x6f4000

```

`libapp.so` size `0x19f1000` 与静态分析得到的段结构（LOAD RW- @0x19f0000）完全吻合，说明基址换算可信。

### 真实 hook（`tools/frida_connect_hook.py`，20 秒）

```
[+] hooked connect @ 0x71c82c87e0
[=] 观测到 9 个不同目标（共 21 次 connect）
    127.0.0.1:36777        x4
    8.147.106.195:9914     x4
    125.77.147.198:1935    x1
    8.8.8.8:65535          x3
    [20:0:0:0:0:0:0:0]:65535 x3
    127.0.0.1:37059        x2
    36.158.250.21:7760     x2
    125.77.147.194:1935    x1
    125.77.147.205:1935    x1
[+] detached cleanly
```

解读：

- `8.147.106.195:9914` — 阿里云，4 次，像长连接业务网关
- `125.77.147.194 / .198 / .205 : 1935` — 同端口三节点，典型负载均衡组（业务 API）
- `8.8.8.8:65535`、`[20:0:...]:65535` — 系统连通性探测，非业务流量
- `127.0.0.1:36xxx / 37xxx` — App 内本地 IPC

**hook 期间脚本零异常、App 无重启、pid 未变（16020）**，证明 16.5.9 能承载真实 hook，不是只能读模块。

## 六、操作纪律（真机）

1. **SELinux 永远保持 Enforcing**，绝不 `setenforce 0`（见 2026-10-31 事故记录）
2. 只用 pid attach，不 spawn（spawn 会重启 App）
3. 只在 `/data/local/tmp` 内读写，不碰其它目录
4. 每轮结束 kill frida-server + `adb forward --remove-all` 回基线
5. hook 脚本只读参数，不改寄存器、不阻断调用
