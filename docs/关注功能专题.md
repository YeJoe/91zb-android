## 一、实验条件与可复现性

- 所有「路由到底存不存在」的判据，都是在本机对着 MuMu 里运行的源 App 隧道打出来的，脚本在 `tools/`。
- 明文隧道协议（源 App `/tunnel/open` 长连接）的帧形如：
  ```json
  {"body":{"room_id":212879817,"menu_id":3,"cp_type":3},"random":47,"method":"POST","uri":"/websock/join"}
  ```
- **关键性质：未知 uri 不会报错，而是统一回 `{"code":0}`（网关兜底）**。因此判断某路由是否存在的方法：
  把「候选路径」与「一定不存在的路径」各打一发，比较响应：

  | 响应 | 含义 |
  |---|---|
  | `{"code":0}` | 路由不存在（兜底） |
  | 任何别的 JSON | 路由存在，返回真实业务结果 |
  | HTML 404 | 这个 vhost 压根不认这个前缀 |

  脚本：`tools/route_scan.py <port>`，候选来自 `tianmei/out_dir/pp.txt`（420 条 `/xxx` 字符串）。

## 四、真实关注接口（来自 pp.txt，仍成立的部分）

> 注意：`/relationship/add` **在明文隧道层不存在**（源 App 17 个 listener 全 404，已逐一验过），它只挂在 libkiwi 的加密 protobuf 通道上，那条通道需要另一套会话，手里的 JWE 进不去（`/go` 网关一律回 `403 用户不存在或超时`）。

### 4.1 两条接口（仅在 libkiwi 加密通道内存在）

```
POST /relationship/add      { userId, followeeId, channelId } → AddFollowReply
POST /relationship/remove   { userId, followeeId, channelId } → RemoveFollowReply
```

证据位置（pp 偏移）：`pp+0x59d40` `"/relationship/add"`、`pp+0x59d48` `"Relationship.addFollow method:"`、
`pp+0x59d58` `"@@@@@@@@@@@@@ go api:addFollow "`、`pp+0x59cb8` `"/relationship/remove"`、
`pp+0x59d10` `List(11)[0,0x4,0x3,0x1,"channelId",0x3,"followeeId",0x2,"userId",0x1,Null]`、
`pp+0x77340` `Field <AddFollowReply._i>`、`pp+0x77358` `Field <RemoveFollowReply._i>`。

### 4.2 三个必须对齐的细节

1. **参数名是 `followeeId`（双 e）**，不是 `podcast_id`，也不是 `followee_id`；
2. **必须带 `channelId`**（`ecy`）和 **`userId`**（自己的用户 id），三缺一服务端按未定义参数处理；
3. 日志里 `go api:addFollow` 说明它**走 `/go/` 加密路径**（`HttpRequest::encryptApiPath` 那套），不是普通 REST。

### 4.3 `podcast_id` == 房间号

2026-10-29 实测：`my_follow` 返回的 `podcast_id` 拿去 `/room/get_list_by_ids` **8/8 全部命中**，`attachment_url` 与关注列表头像逐字节一致。
所以关注链路里 `followeeId` 直接传**房间号**即可，不需要额外映射表。

### 4.4 顺带拿到的读接口（pp.txt）

| 接口 | 方法 | 用途 |
|---|---|---|
| `/user_follow/my_follow` | POST `{}` | 我的关注列表（`result[].podcast_id`） |

## 五、写关注实际走的通道：抓包证据（决定性）

在设备上 `tcpdump -i any` 抓了一次完整「点关注 → 取消关注」（用户确认按钮状态变了）：

- **外网零 HTTPS 请求**：只有 RTMP 流（222.186.20.158:1935）和 CDN 图片（18.245.78.x:80）。说明关注请求没走公网，就在本机回环隧道里；
- 回环里**搜不到任何明文 `follow`/`relationship`**（含 gzip 解压后再搜）；
- 业务 vhost 上有一条**从第一个字节就是密文**的裸流连接（无 HTTP 请求行），另有 `/tunnel/open` 的 WS 代理连接（明文 JSON 帧，只有 hello/websock 那几条）。

在直播间点「+关注」，前后对比：关注数 **18 → 19** 确实生效；1.9MB / 1748 个包里，`POST` 请求 **0 条**，`relationship` **0 次**，`followeeId` **0 次**。
点击后 1.7 秒出现一条到**本地端口 44697** 的短连接，0.1 秒内结束：

| 方向 | 字节 | 内容 |
|---|---|---|
| 请求 | 86 | `825478da0dca210e80300c40d1bb7c3d3170f42c...` 全密文 |
| 响应 | 102 | `82e0e5c2621e07d461da19888c9f558e...` 全密文 |

两边首字节都是 `0x82`，像是协议魔数/版本。

> **结论：写操作 = 一条本地 TCP 短连接 + 86 字节加密二进制，由 SDK 解密后转发。HTTP 那条路上根本没有这个动作。**

### 5.1 密文帧结构指纹

某条连接上 7 条请求帧，长度全是 96 字节，**只有第 3 个 16 字节块不同，前后块完全一致**：

```
块0 efe02617fa857ce20d362b754d715d64   ← 两次不同会话（间隔数分钟）完全相同
块1 e7a7239b031fb9a95f43df64cc403322
块2 95d695e15c70f64410b73468ce7c62ec
块3 304cc1dc301289e85ad201a38c64bae2   ← 唯一变化的一块
块4 5e7336164ac459b00bb185c0d023c07a
块5 9139d245c69595ae7f68fd4fb320c7a7
```

推论：
1. 16 字节分组、块间互不影响 → **ECB 类分组加密**（CBC 会让第 4、5 块一起变，实测没变）；
2. 明文可还原为「8 字节帧头 + 87 字节 JSON」，`"random":43` 里的数字正好落在第 3 块内——解释「为什么只有第 3 块变」；
3. 两次会话块 0 完全一致 → 密钥是**静态或按小时固定**的，不是每连接协商。

### 5.2 已排除的密钥来源

- `tools/rabbit.py` 里那套 `MD5(SALT + 小时 + token)`：**SALT 在当前版本 libapp.so 里根本不存在**（UTF-8 / UTF-16 都搜不到），是 8.1.7 时代实现，8.5.3 已换掉；
- 342 组派生候选（md5/sha256 × token/jwe/uid/渠道/昵称/appKey × 多种盐）全部不匹配；
- 对 `libapp.so`(26MB) + `libkiwi.so`(6.6MB) 做**全偏移 16 字节窗口穷举**（3 千万次 AES 试解，56 字节已知明文做判据），未命中 → 密钥不是二进制裸常量，是运行时算出来的；
- `/go/<blob>` 路线存在，但发请求只回 `403 {"code":-10000,"msg":"用户不存在或超时，请重新登录"}`——go 网关要另一套 session，手里 JWE 喂不进去；且解出的 `/go` 响应实为 `license.vod2.myqcloud.com/.../v_cube.license`（播放器授权校验），不是业务接口。

### 5.3 dex 解析：SDK 只是管道，无可反射的加解密

最小 DEX 解析器 `tools/dex_scan.py`（仅标准库）展开 `app/src/main/assets/kiwi-sdk.jar` → `classes.dex`：

```
classes.dex  size=5.5MB  classes=5627  methods=42997  strings=42195
native 方法 495 个
```

`com.kiwi.sdk` 仅 21 个类，核心 `Kiwi` 的 25 个方法全是隧道管理（`Init`/`InitWithListener`/`RestartAllServer`/`ServerToLocal`/`ForceRestartServer`/`SimpleDns`/`NetworkStat`/`SendLog`/`MonitorNetworkState` 等，**无任何 encrypt/decrypt/cipher 方法**）。
整个 dex 里的 23 个加解密方法全属第三方：`com/netease/nis/basesdk/EncryptUtil`（网易易盾）、`com/tencent/liteav/...`（腾讯直播 SDK）。

**由此修正架构理解**：本地 17 个 listener 是**透明 TCP 代理**，不是 HTTP 网关——明文 HTTP 能直接穿过（故 `/user_follow/my_follow` 等读接口可用），App 自己发的 86 字节二进制帧也原样穿过，由**云端**解密。
**「反射调 SDK 的 Decrypt」这条路不存在**，此前的设想作废。

### 5.4 帧格式（终局确定）

```
82 | len | 78 da 0d ca | ... 帧体 ... | seq
 ↑    ↑       ↑                         ↑
 |    |       |                         末字节，逐帧递增（观察到 9d→a5）
 |    |       固定魔数，明文
 |    长度（总长 - 2）
 固定首字节
```

所有帧里**完全恒定**的字节位置：`0, 2, 3, 4, 5, 8, 10, 13` → 帧头明文、帧体密文。

- **关键结论：keystream 是「位置稳定」的**——同一会话内同命令连发两次，帧只差 **3 字节**（位置 18、84、86）；若是每次随机 IV 会完全不同。
- 跨簇（不同命令）差异 67~73 字节；簇内差异 3~4 字节。
- 两轮抓包对比（`tools/bin_probe.py`，把 86 字节帧原样打到当前 17 个端口）**全部无响应**——注意端口号每次 App 重启重新分配，重放必须在同一 App 实例存活期内做。

### 5.5 确定性实验：无法通过改帧伪造任意主播（终局结论）

设计：快照 A `my_follow` 全量 = 20 条 → 抓包中关注两个新主播 → 快照 B = 22 条，新增 `[407445055, 1165187615]`。在全部帧对里找「差异窗口 == 两 id 的 XOR（4/8 字节 × 大小端）」——**没有命中**（11 个帧两两差异矩阵里，没有任何一对只在 8 字节窗口内不同）。
`#5 vs #10`（同一命令、两个不同主播）差异集中在 `[44..51]` 共 8 字节，但两 id 的 XOR 高 4 字节必为 0，实测 XOR 高 4 字节是 `0x1609a750` 不为 0 → 这 8 字节不是「int64 形式的 id」。
`/user_follow/my_follow` 返回列表**按 podcast_id 升序**（非关注时间），无法判断「最近关注了谁」。

> **最终判断**：关注帧的 id 字段**不是 podcast_id 的线性（XOR）变换**，无法通过修改现成密文换目标；加密大概率是「带密钥的块加密 / 带 nonce 的 AEAD」，密钥运行时派生，二进制无裸常量。**通过私有二进制协议实现「关注任意主播」不可行。**

## 六、读接口的坑：`/user_follow/my_follow` 分页

> 一句话：`POST /user_follow/my_follow` **一页固定 20 条**，旧代码只发一次 `{}` 就当全集，所以服务端 303 位关注，App 只显示 21 位（20 + 1 条本机关注）。这就是「真实关注列表和服务端不一样」的原因。

### 6.1 分页规则（逐条打出来的）

| 请求体 | 结果 |
|---|---|
| `{}` | 等价 `page:1`，回 20 条 |
| `{"page":1}` | 20 条 |
| `{"page":2}` | 20 条（不同的 20 条） |
| `{"page":16}` | 3 条 |
| `{"page":17}` | 0 条 |
| `{"page":0}` | 0 条 ← **page 从 1 开始**，0 不是第一页 |
| `{"pageSize":100}` | 仍然 20 条 ← 服务端不认 pageSize |
| `{"pageIndex":1}` | 20 条（第一页，`pageIndex` 被忽略） |

两个坑：
1. **`has_next` 恒为 1**，翻到最后一页也是 1，不能拿它判断结束；
2. **`count` 不可靠**：报 299，实际把 16 页去重后是 **303** 条。唯一可靠终止判据是「本页不足 20 条 / 空页」，不要用 `count` 算页数（299 条实际 16 页，按 count 算只有 15 页）。

### 6.2 现场数字

| 位置 | 数量 |
|---|---|
| 服务端 `my_follow` 全量（uid 1422303235） | **303**（`count` 报 299，对不上） |
| TM Live 旧代码显示 | **21**（= 第 1 页 20 条 + 本机独有 1 条） |

### 6.3 修法（`LiveRepo.pullFollows()` 自动翻页）

- 第 1 页不满 20 条 → 直接收工（多数账号一发就够，如临时号 423344474 只有 17 位）；
- 否则 5 页一波并发往后翻，遇空页/不满页停；
- 上限 50 页（1000 位）兜住被写坏的数据。
- 实测该账号：**16 个请求、4 个来回、拿到 303 个唯一 id**，完全对得上服务端。
- 顺手修掉「关注整片消失」隐患：`pullFollows` 用 **null 表示请求失败**，`fetch()` 拿到 null 时保持上一次结果不动（以前失败返回空 Map 直接写回 `followIds`，一次网络抖动就清空列表）。

### 6.4 剩下的 1 条差异不是 bug

`AppContainer.followIdSet()` = 服务端关注 ∪ 本机收藏。本机多出的那条（736714165 たた多多也）是用户在 TM Live 里点的关注，而 App 写接口够不到服务端，只落本机。现已在 `FollowScreen` 单独列成「仅本机 · 服务端没有」一组，不再混在「未开播」里。
