# 弹幕一直 404：根因与修复（2026-10-30 二修）

> 承接 [弹幕接口实测-端口与判据.md](弹幕接口实测-端口与判据.md)。那篇解决了「判据写错」
> （把 405 当失败），这篇解决「判据对了，但端口根本进不了候选表」。

---

## 一、症状

判据改成 405 之后，设置页仍然显示：

```
:端口 join 回 404（试了 N 个端口）
```

且 `N` 很小（2~4 个），说明候选表里几乎没东西 —— 不是端口连不上，是**没被收进来**。

---

## 二、根因：三个叠加的缓存/时序缺陷

### 缺陷 1：失败也写缓存，把正确端口永久毒化

`LiveRepo.verifyWsPorts()` 原实现：

```kotlin
val fresh = list.filter { now - (wsTriedAt[it] ?: 0L) > 60_000L }   // 失败也记时间
...
fresh.forEach { wsTriedAt[it] = now }                              // ← 无条件写
if (hits.isNotEmpty()) wsVhosts = (hits + cached).distinct()       // ← 只在成功时更新结果
```

时序杀伤链：

```
隧道 init 完成
  └─ listener 刚 bind，转发链路还没接通（实测要 1~2 秒）
       └─ 第一次 verifyWsPorts → 全部失败
            └─ wsTriedAt 全写上 now（60 秒内不再重验）
            └─ hits 为空 → wsVhosts 保持空
                 └─ 接下来 60 秒，verifyWsPorts 永远返回空表
                      └─ 候选表退化成 tunnel.port（/room 组）
                           └─ join 必然 404
```

**关键点**：结果是「对」的（确实连不上），但缓存策略让它**永远没有第二次机会**。

### 缺陷 2：`probeWsVhosts()` 把空结果也缓存了 60 秒

```kotlin
if (now - wsVhostsAt < 60_000L) return wsVhosts   // wsVhostsAt 无论有无结果都前进
```

和缺陷 1 同构：第一轮必然失败，然后整整一分钟都直接返回空。

### 缺陷 3：`take(MAX_PROBE_PORTS)` 截断

```kotlin
verifyWsPorts(listenPorts().sortedDescending().take(MAX_PROBE_PORTS))
```

隧道端口从**临时端口段**随机分配（实测 11689 / 34199 / 37679 / 45209…），
截断前 64 个在端口表变大时会把真 IM 端口切掉。

### 缺陷 4（次因）：探测超时 1.2 秒太短

隧道链路是「本地 listener → 网关 → 远端 nginx」，首包要走完整条链路。
冷启动头几秒，同一个端口 1.2 秒连不回是常态，直接判 false。

---

## 三、修复

| 位置 | 改法 | 效果 |
|---|---|---|
| `verifyWsPorts()` | **只缓存成功**，失败的下轮立刻重试 | 隧道稍晚就绪也能自动纠正 |
| `verifyWsPorts()` | 成功集每轮用**本轮候选集**做交集 | 端口重排后旧记录自动失效 |
| `probeWsVhosts()` | 只有**非空结果**才推进时间戳 | 空结果下次立刻重扫 |
| `probeWsVhosts()` | 去掉 `take(MAX_PROBE_PORTS)` | 真端口不会因截断被切掉 |
| `wsJoinReachable()` | 超时 1200ms → **2500ms** | 覆盖冷启动抖动 |
| `wsJoinReachable()` | 4xx 一律读 body，含 `bad token` / `method not allowed` 也算命中 | 网关改判据时不误杀 |
| `wsJoinReachable()` | 探测时**带上 JWE** | 更接近真实请求，减少鉴权层干扰 |

代价：隧道完全没起时，每次重连多花约 2.5 秒（并发 8 路）。
换来的是「端口明明对却被判死」这个最恶心的故障消失 —— 这笔账划算。

## 四、新增：端口诊断

设置页 → 弹幕 → **诊断端口**。

会对每个候选端口打一发 `POST /websock/join`，直接列出：

```
弹幕端口诊断（判据：明文 POST /websock/join → 405 才算 IM vhost）
共 14 个端口：
  :37679  HTTP 405  ✅ IM vhost  {"msg":"bad token, please login!","code":-10000}
  :44775  HTTP 403  ❌ 别的 vhost 鉴权层  {"msg":"设备登陆中","code":-10000}
  :14369  HTTP 403  ❌ 别的 vhost 鉴权层  {"msg":"设备登陆中","code":-10000}
  :37783  HTTP 404  ❌ 不挂 /websock
  :36027  HTTP -1   ⌛ 超时/连不上

命中数：1
```

排查时先看这个，三种情况分别对应三种病：

| 诊断输出 | 含义 | 下一步 |
|---|---|---|
| 有 `✅ IM vhost` | 端口找对了，404 是别的原因 | 看重连后 `status` 是否变成「已进房 :端口」 |
| 全 `❌`，但端口列表有十几个 | 隧道起了，但没有组挂 `/websock` | 源 App 那边可能没进过房；或试开「源 App 后台隧道」 |
| 只有 0~2 个端口 | 隧道根本没起来 | 看设置页「隧道」面板的 `diag` |

---

## 五、仍然要记住的三条铁律

1. **`/websock/*` 只挂在 IM vhost 上**，拿 `/room` 的端口去连一定 404 —— 这个 vhost 身份
   **只能靠 405 判据反推**，组名（`kiwi_im`）只是线索，不可信。
2. **端口每次冷启动都重排**，任何写到磁盘/写死常量的端口都会在下一次失效。
3. **隧道是"长连接代理"**：上游断了它可能既不 FIN 也不 RST，表现成「已进房但没弹幕」。
   `LiveDanmaku` 靠「30 秒无帧就 ping，90 秒无数据重连」探出来。

---

## 六、验证方法

1. 重装 App，设置页确认「隧道就绪 :端口」
2. 点「诊断端口」→ 必须出现至少一个 `✅ IM vhost`
3. 进任意真人直播间 → 设置页弹幕那行应显示 `已进房 :37679` 之类
4. 热门房 20 秒内应有 100+ 条推送；冷清房 0 条属正常（房间真没人说话）
