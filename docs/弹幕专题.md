# 弹幕专题（2026-10-30 整合）

> 本篇由以下三篇合并而来，结论以 405 判据与 typ 过滤规则为准：
> `弹幕接口实测-端口与判据.md`、`弹幕分类与过滤.md`、`弹幕404根因与修复.md`。
>
> **两句话结论**：
> 1. **弹幕接口端口判据：明文 `POST /websock/join` 回 HTTP 405 才是 IM vhost（即成功），不要把 405 当失败**；回 403 一律是别的业务 vhost 鉴权层，不是命中。
> 2. **过滤规则：弹幕里只有 `typ=32`（普通聊天）和 `typ=4`（@提及）是观众发言，其余全是平台 / 博彩 / 运营消息**；分类依据 `menu_id`（真人 5/101/102/103/104/105/108，博彩 8/8000~8013）。

## 一、接口还在不在？端口固定吗？

- 接口**没变**：仍是 `/tunnel/open`（WS 升级）→ `/websock/join` → `room_msg` 推送。
- 端口**不固定**：同一台机器三次冷启动分别是 `11689` / `34199` / `37679`。
  隧道 listener 每次进程启动时重新 bind，端口由系统从临时端口段分配。任何写死端口、或只在启动时算一次长期缓存的做法都会在某次重启后失效。
- 为什么 tcpdump 看不到明文：源 App Dart 层走 `libkiwi.so` 加密隧道，tcpdump 抓 `lo` 只能看到 `[len][seq][crc][ciphertext]` 二进制流。明文 HTTP 只出现在少数不加密 vhost 上。所以改用**协议探测**：对每个本地监听端口发同样请求，用响应差异反推 vhost 身份。

### 进房验证实测

在 37679 上对 `live_in=1` 且 FLV 探活通过的房间做真实 join：

```
=== 房间 87839418 menu=102 ===
  join status=200 code=0
   [17.4s] room_msg  赢钱点仨美女: @備胎呆賊_ztnp 看见内裤了吗
   [18.6s] room_msg  年少金魚_szetch: 下注 120 元
  → 20s 内收到 130 条推送
```

推送有三类 `ctl`，只取 `room_msg`：

| ctl | 内容 | 处理 |
|---|---|---|
| `room_msg` | 聊天 / 礼物 / 下注 / 开奖 | 按 `content.typ` 分类，只留 32·4（聊天）和 3（礼物） |
| `room_player` | 进场用户（每次带完整用户对象，几十条一批） | 丢（占了推送量约 110/130，必须丢否则刷屏） |
| `room` | 房间元信息变更 | 丢 |

真实推送速率：热门房 20 秒 **130 条**，冷清房 7 条——全是实时，没有历史回填。

## 二、判据：405 才是 IM vhost（核心，别再写错）

对 6 个端口同时发**明文 POST** `/websock/join`（body `{"room_id":1,"menu_id":1,"cp_type":3}`）：

| 端口 | HTTP | body | 是不是 IM vhost |
|---|---|---|---|
| **37679** | **405** | `{"msg":"bad token, please login!","code":-10000}` | ✅ 是 |
| 44775 | 403 | `{"msg":"设备登陆中","code":-10000}` | ❌ 否 |
| 14369 | 403 | `{"msg":"设备登陆中","code":-10000}` | ❌ 否 |
| 37783 | 403 | `{"msg":"用户不存在或超时，请重新登录","code":-10000}` | ❌ 否 |
| 36027 / 38321 | 超时 | — | ❌ 否 |

**为什么 405 是正确指纹**：`/websock/*` 这个 location **只接受 WS 升级**，明文 POST 在 nginx 的 method 层就被挡（405），根本到不了应用层；body 里那句 `bad token` 是「没带 JWE 头」的必然结果，**和 vhost 对错无关**。
而 403 那几个是**别的业务 vhost 的鉴权层**（「设备登陆中」是登录态检查），也回 JSON、也是 `code:-10000`，看着像命中——只看「是不是 JSON」就会误收。

**对应代码判据**（`LiveRepo.wsJoinReachable`）：原判据 `responseCode !in 200..299 → false` 会把真端口（回 405）直接判死，命中列表永远为空；修正为 **405 为准、403 + bad token 兜底**，且 4xx 一律读 body。

> 真机诊断实测（run 36，24 个监听端口）：405 命中 **1 个**（`bad token` body，IM vhost :33579）；403 共 5 个（别的 vhost 鉴权层）；404 共 15 个（不挂 `/websock`）；超时 3 个。
> 三个直接落地结论：
> 1. 判据对但命中率极低（1/24），所以「候选表里必须包含全部监听端口」这条不能省——靠组名（`kiwi_im`）猜的端口这次没命中，真正能用的是扫描扫出来的那个；
> 2. 403 的 body 分两种，都不能当命中：`请登录`/`用户不存在或超时` 是别的业务 vhost 鉴权层，只有 `bad token, please login!` 才说明请求到了 `/websock` 鉴权；
> 3. 诊断本身该把结果留下：现在 `diagnoseWs()` 把命中端口写进 `wsVhosts`，界面拿到含 `✅` 结果后直接 `danmaku.restart()`——一次点击，诊断即修复。

## 三、404 根因：判据对了还 404（四个叠加缺陷与修复）

### 缺陷 1：失败也写缓存，把正确端口永久毒化

`LiveRepo.verifyWsPorts()` 原实现对失败也记 `wsTriedAt`、且只在成功时更新 `wsVhosts`：隧道 init 完成瞬间 listener 刚 bind、转发链路还没接通（实测要 1~2 秒），第一次 verify 全失败 → 全写上 now（60 秒内不再重验）→ hits 空 → wsVhosts 保持空 → 候选表退化成 `tunnel.port`（/room 组）→ join 必然 404。**结果是「对」的，但缓存策略让它永远没第二次机会。**

### 缺陷 2：`probeWsVhosts()` 把空结果也缓存 60 秒

首轮必然失败，然后整整一分钟直接返回空。同构于缺陷 1。

### 缺陷 3：`take(MAX_PROBE_PORTS)` 截断

隧道端口从临时端口段随机分配（实测 11689 / 34199 / 37679 / 45209…），截断前 64 个在端口表变大时会把真 IM 端口切掉。

### 缺陷 4（次因）：探测超时 1.2 秒太短

隧道链路是「本地 listener → 网关 → 远端 nginx」，首包走完整链路，冷启动头几秒同一端口 1.2 秒连不回是常态，直接判 false。

### 修复

| 位置 | 改法 | 效果 |
|---|---|---|
| `verifyWsPorts()` | **只缓存成功**，失败的下轮立刻重试 | 隧道稍晚就绪也能自动纠正 |
| `verifyWsPorts()` | 成功集每轮用**本轮候选集**做交集 | 端口重排后旧记录自动失效 |
| `probeWsVhosts()` | 只有**非空结果**才推进时间戳 | 空结果下次立刻重扫 |
| `probeWsVhosts()` | 去掉 `take(MAX_PROBE_PORTS)` | 真端口不因截断被切掉 |
| `wsJoinReachable()` | 超时 1200ms → **2500ms** | 覆盖冷启动抖动 |
| `wsJoinReachable()` | 4xx 一律读 body，含 `bad token`/`method not allowed` 也算命中 | 网关改判据时不误杀 |
| `wsJoinReachable()` | 探测时**带上 JWE** | 更接近真实请求，减少鉴权层干扰 |

代价：隧道完全没起时，每次重连多花约 2.5 秒（并发 8 路）。换来「端口明明对却被判死」的故障消失。

### 第三种病：候选表只有两三个端口（run 36 后仍报 404）

症状：`弹幕未连接 · 断开重连：:56067 join 回 404（试了 2 个端口）`，但「诊断端口」能列 24 个端口且命中 `:33579`。差别在**取候选的时机与缓存**：进播放页那一刻隧道刚 init、listener 表短，一轮全假阴性；假阴性虽不写缓存，但 `wsVhostsAt` 一旦被某次成功置位，接下来 60 秒直接复用旧结果不再重扫；候选表退化成 `tunnel.imPort` + 列表端口（`:56067` 这种「列表/组端口」，join 必然 404），WS 每轮只试两个。

修复（两条互补）：`diagnoseWs()` 命中端口写进 `wsVhosts`（+`wsTriedAt`/`wsVhostsAt`），设置页拿到含 `✅` 结果后直接 `danmaku.restart()`——点一次诊断即修复；`AppContainer` 弹幕候选**不足 3 个就 `probeWsVhosts(force=true)` 强制重扫**（阈值 3 而非 2：`imPort`+`tunnel.port` 天生凑出 2 个，恰恰是「什么都没筛出来」的典型形态）。

### run 37 实测：405 命中 2 个，WS 仍不通

`共 28 个端口，命中 2 个：:34179 :49346`，但状态行那个 `:5839`（最后一个端口）把前两个的失败原因覆盖了。修法：
- `pumpOnce` 记录**每个**端口的失败原因（`/` 分隔），不再只留最后一个；
- `join` 失败时带上 body 的 `msg`/`message`，区分 nginx 404（HTML）与业务网关 404（`路由未找到`）；
- 设置页加一行「凭证：appToken=… · JWE=…」，`appToken` 为空时握手会缺 token。

### run 38 实测：真正的病是「没有会话 token」

```
链路：断开重连：:38105 join 回 403 · bad token, please login!
      / :43991 join 回 403 · bad token, please login!
      / :23028 join 回 404（这个 vhost 不挂 /websock）（试了 3 个端口）· 本次已收 0 条
端口：im=38105 · 列表=23028
凭证：appToken=空（握手会缺 token）· JWE=有
弹幕候选端口（按序试 join）：38105 → 43991 → 23028
```

结论：端口是对的（`:38105`/`43991` 回 403 + JSON `bad token`，说明请求已穿过网关到了 im 鉴权层）；身份是缺的（`appToken=空`）；于是 `bad token` 是必然结果。

**405 判据验的是 nginx 方法层，跟 token 无关**，于是出现矛盾组合：诊断命中 2 个 405（只说明挂 `/websock`，与身份无关） vs 真进房 403 bad token（WS 之后 im 走应用层鉴权才看 token） vs 列表接口零凭证也能用（公开接口不需要 token，「不用填 token」的错觉由此而来）。实际上进房要**两个**凭证：`?token=<32hex>`（会话）+ `authorization: Bearer <JWE>`（长期）。**JWE 可用内置默认值，会话 token 不行——它是每个源 App 会话一份、只存在内存的。**

修复（`LiveDanmaku.run` / `ui/SettingsScreen` / `LiveRepo.diagnoseWs`）：token 为空/格式不对时**不再轮询端口**，直接显示「缺会话 token：设置 → 弹幕 → 会话 token 填 32 位 hex」；弹幕分组新增**会话 token 输入框 + 保存并重连**（校验 32 位 hex）；诊断输出头部加「会话 token：空 / ab12cd…」，命中 405 但 token 为空时补 ⚠️。

取 token 实操：`源 App 保持后台 → python tools/token_export.py → 输出里的【会话 Token】→ DC Live → 设置 → 弹幕 → 会话 token → 保存并重连`。它是**会话级**的，源 App 冷启动/重新登录/掉线重连都可能换一批；`/room/get_list_by_ids` 不需要它（所以导出工具说明里写「不用填」），但 `/websock/join` 需要——这两件事旧文档被混成一句，是这次排查最贵的弯路。

### 还需不需要扫二十几个端口？要，但不必每轮都扫

会话 token 管**身份**（让不让你进房），端口管**路由**（请求能不能到处理 `/websock` 的 nginx）；同一个 `:38105`，token 空时回 403 bad token、填上就进房（端口没变）；`:23028`（业务 api vhost）token 再对也回 404（nginx 不认这个 location）。所以「知道缺 token」不能省掉找端口，只能省掉「缺 token 时」找端口（已在上面改成直接跳过）。

原实现每轮重连先算全量候选（groupPorts 逐个验 → 扫本机全部 LISTEN 24~28 个 → 才轮到 WS），为试 1 个端口先发 24 个 HTTP。改成两档：

| 档 | 候选 | 请求数 | 什么时候跑 |
|---|---|---|---|
| 快 | `goodPort` → `imPort` → 上次 405 命中（`cachedWsPorts()`） | **0**（只读现成值） | 每轮第一轮 |
| 全 | 组端口 405 验 + 扫全部 LISTEN + 兜底端口 | 24~28 | 快路径 join 失败之后 |

快路径失败**不报状态**，直接扩到全量再试一轮（否则状态行会闪一下错误）。缓存判据从「60 秒 TTL」换成**端口表指纹**：LISTEN 端口集合一样 → 结论有效；一变 → 立刻重扫（原 60 秒 TTL 两边都不对：端口可能 5 秒重排也可能 10 分钟没动）。`verifyWsPorts()` 用组端口收缩过结果集后会作废指纹；设置页「诊断端口」扫全了才写入指纹，被 `limit` 截断就作废。顺带删掉无人读的 `wsTriedAt` / `wsVhostsAt`（被指纹替代）。

## 四、诊断端口（设置页）

设置页 → 弹幕 → **诊断端口**，对每个候选端口打一发 `POST /websock/join`，直接列出：

```
弹幕端口诊断（判据：明文 POST /websock/join → 405 才算 IM vhost）
共 14 个端口：
  :37679  HTTP 405  ✅ IM vhost  {"msg":"bad token, please login!","code":-10000}
  :44775  HTTP 403  ❌ 别的 vhost 鉴权层  {"msg":"设备登陆中","code":-10000}
  :14369  HTTP 403  ❌ 别的 vhost 鉴权层  {"msg":"设备登陆中","code":-10000}
  :37783  HTTP 404  ❌ 不挂 /websock
  :36027  HTTP -1   ⌛ 超时/连不上
命中数：1
```

排查先看这个，三种情况对应三种病：

| 诊断输出 | 含义 | 下一步 |
|---|---|---|
| 有 `✅ IM vhost` | 端口找对，404 是别的原因 | 看重连后 `status` 是否变成「已进房 :端口」 |
| 全 `❌`，但端口列表有十几个 | 隧道起了，但没有组挂 `/websock` | 源 App 可能没进过房；或试开「源 App 后台隧道」 |
| 只有 0~2 个端口 | 隧道根本没起来 | 看设置页「隧道」面板 `diag` |

## 五、分类与过滤（实测：462 条消息 / 31 真人房）

> 采样：`tools/danmaku_probe.py`，真人分类（`menu_id` 5/101/102/103/104/105/108）下 31 个房间、462 条消息，每房拉 `/websock/history_msg` + 监听 3 秒实时推送，原始样本落 `assets/data/dm.jsonl`（不入库）。规则实现：`tools/danmaku_filter.py`（唯一规则源）、`site/dm_filter.js`（网页端手抄版）。

### 判据从哪来

消息对象（`/websock/history_msg` 与 `ctl=room_msg` 推送同构）：

```json
{
  "id": 25495396872, "user_id": 1654380872, "nickname": "只是冷の匆匆",
  "content_type": 1, "optcode": 32,
  "content": "{\"text\":\"我喜欢老头乐\",\"typ\":32}", "create_time": 1793210541
}
```

三个字段决定一切：

| 字段 | 取值 | 说明 |
|---|---|---|
| `content_type` | `1` / `8` | 大类：`1`=纯文本，`8`=结构化（JSON 里带自己的 `typ`） |
| `optcode` | 顶层 | 只有部分消息带；`content_type=8` 时经常是 `null` |
| `content.typ` | 内嵌 | **最可靠**，几乎每条 `content_type=8` 的消息都有 |

⚠️ 坑：`content_type=8` 的消息顶层 `optcode` 常是 `null`，真正类型码在内嵌 JSON 的 `typ`。只读顶层字段会把下注/结算全判成「未知」。规则取码顺序：`content.typ → optcode → content.optcode`。

|---|---|---|---|---|
| `32` | 1 | 普通聊天 | `{"text":"我喜欢老头乐","typ":32}` | **保留** |
| `4` | 1 | @提及 | `{"text":"@凯凯哎哎啊 哥","typ":4}` | **保留**（也是聊天） |
| `3` | 8 | 送礼物 | `{"item_id":5020,"count":1,"combos":1}` | 保留（可选关） |

| `20` | 8 | 结算 / 中奖 | `{"pay_amount":392,"cp_name":"百人牛牛"}` | 丢弃 |
| `23` | 8 | 开奖 | `{"pre_draw_code":[2,2,2],"memo":"6 小 双","cp_type":3}` | 丢弃 |

### 关键词兜底：为什么还需要

类型码能覆盖 99%，但两类例外：① 纯文本系统广播没有 `typ`（如 `麻将牛牛财神提款 … 速来围观！`，靠 `desc` 传播）；② 伪装成聊天的引流文案（`typ=32`，但内容是「送跑车解锁 22 部福利视频…」），只能从文本特征认。规则分两层：

```
         ┌─ 有类型码 ─→ 按 TYP_KIND 定 kind ─→ kind ∈ {chat,gift} ? 保留 : 丢弃
消息 ────┤
         └─ 无/未知类型码 ─→ 关键词打分 ─→ 命中博彩/广告/系统词 ? 丢弃
                                          └ 否则按文本是否像聊天决定
```

关键词表（`danmaku_filter.py`）：

| 词表 | 用途 | 举例 |
|---|---|---|
| `BET_WORDS` | 博彩/盘口 | 下注、结算、开奖、百家乐、快三、七星、东方彩票、收入囊中 |
| `AD_WORDS` | 引流/站外拉人 | 速来围观、加微、QQ群、邀请码、下载APP、稳赚 |
| `SYS_WORDS` | 平台运营通知 | 完成了主播、本场心愿、升级为、排行榜 |
| `SPAM_PATTERNS` | 硬广告特征 | `http://`、`.com`、`+v` |
| `CHAT_AD_WORDS` | 伪装成聊天的引流 | 加私人、福利视频、解锁、一对一、包本人 |

**关键取舍：真人聊天不做博彩词过滤**——`typ=32` 直接放行，只拦链接和联系方式（观众会聊「这把下注多少」「刚才开奖多少」，用博彩词表筛会误杀）。`CHAT_AD_WORDS` 只在**长度 ≥ 25 字**时才判（否则「一对一多久」「几个福利视频」这类观众追问会被误伤）。伪装文案判定收敛为三条：长度 ≥ 110 字 → 刷屏；长度 ≥ 60 字且含 2 个以上表情（💖💞💦🌊👍🉑）→ 长文+表情轰炸；长度 ≥ 25 字且命中 `CHAT_AD_WORDS`。

### 落地

Python 端：`import danmaku_filter as f; r = f.classify(item)`、`f.filter_items(items, keep=('chat','gift'))`。`tools/build_danmaku.py` 把 `assets/data/dm.jsonl` 压成 `site/dm_samples.js`。
网页端：`site/dm_filter.js` 导出 `window.DmFilter.classify(...)` / `filter(...)`，聊天区右上角开关「只看聊天」（默认，渲染 `kind ∈ {chat,gift}`）/「全部」（非聊天带灰色标签，悬停看判定原因）。

### 已知边界

- 无类型码的纯文本广播只能靠词表，词表会漏新文案；漏了在 `danmaku_filter.py` 加词并同步 `site/dm_filter.js`（两边必须同时改）；
- `typ=18` 语义未确认，暂按系统消息丢弃；
- 昵称里的广告（昵称直接叫「XX 娱乐城」）不被过滤（消息体文本干净），要对昵称做同套词表判定属产品取舍，未默认开启；
- 采样只覆盖真人分类房间；盘口房（`menu_id` 8000~8013）博彩占比更高，但不影响规则本身。

## 七、排查手册（下次再 404 先看这三行）

1. 设置页「弹幕」显示 `已进房 :XXXXX` → 正常，端口就是它；
2. 显示 `:端口 join 回 404（试了 N 个端口）` → 候选全错，看下一行端口列表；
3. 端口列表只有 1~2 个 → `groupPorts` 和 `/proc` 都没拿到端口，是隧道没起来（看「隧道」面板），不是弹幕问题。

**三条铁律**：
1. `/websock/*` 只挂在 IM vhost 上，拿 `/room` 的端口去连一定 404——vhost 身份**只能靠 405 判据反推**，组名（`kiwi_im`）只是线索不可信；
2. **端口每次冷启动都重排**，任何写死/常量的端口下次失效；
3. 隧道是「长连接代理」：上游断了它可能既不 FIN 也不 RST，表现成「已进房但没弹幕」——`LiveDanmaku` 靠「30 秒无帧就 ping，90 秒无数据重连」探出。
