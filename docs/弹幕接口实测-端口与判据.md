# 弹幕接口实测：真实端口与判据（2026-10-30）

> 目的：确认源 App 的弹幕接口到底在哪、端口是否固定、我们为什么一直 404。
> 环境：MuMu 模拟器 Android 15（emulator-5554）+ 天美 8.5.3（`com.l95c2450d7.f68bb4e2d5`）
> 方法：`/etc/hosts` 无关，直接抓 loopback + 对全端口做协议探测。

---

## 一、先说结论

| 问题 | 结论 |
|---|---|
| 接口变了吗 | **没有**。仍是 `/tunnel/open`（WS 升级）→ `/websock/join` → `room_msg` 推送 |
| 端口固定吗 | **不固定**。同一台机器三次冷启动分别是 `11689` / `34199` / `37679` |
| 为什么 404 | 拿成了 `/room` 那个 vhost 的端口。`/websock/…` 只挂在 IM vhost 上 |
| 判据是什么 | **明文 POST `/websock/join` 回 405** 的才是 IM vhost；回 403 的一律不是 |
| 真实推送速率 | 20 秒 **130 条**（热门房），冷清房 7 条 —— 全是实时，没有历史回填 |

## 二、为什么 tcpdump 看不到明文

源 App 的 Dart 层请求走的是 `libkiwi.so` 的加密隧道：tcpdump 抓 `lo` 只能看到
`[len][seq][crc][ciphertext]` 这种二进制流（抓包里那条 104KB 的连接就是它）。
明文 HTTP 只出现在**少数不加密的 vhost** 上（比如节点列表 `{"code":0,"ctl":0,"node":[…]}`）。

所以「抓包看接口」这条路在源 App 上走不通，改用**协议探测**：
直接对每个本地监听端口发起同样的请求，用响应差异反推 vhost 身份。

## 三、端口是动态的（三次冷启动实测）

| 时刻 | 源 App 端口数 | IM vhost 端口 |
|---|---|---|
| 10-29 深夜 | — | `11689` |
| 10-30 14:15（TM Live 冷启动） | 24 | `34199` |
| 10-30 14:19（天美冷启动） | 18 | `37679` |

**隧道 listener 是每次进程启动时重新 bind 的**，端口由系统从临时端口段分配。
任何把它写死、或者只在启动时算一次就长期缓存的做法都会在某次重启后失效。

## 四、判据：405 才是 IM vhost

对 6 个端口同时发**明文 POST** `/websock/join`（body `{"room_id":1,"menu_id":1,"cp_type":3}`）：

| 端口 | HTTP | body | 是不是 IM vhost |
|---|---|---|---|
| **37679** | **405** | `{"msg":"bad token, please login!","code":-10000}` | ✅ 是 |
| 44775 | 403 | `{"msg":"设备登陆中","code":-10000}` | ❌ 否 |
| 14369 | 403 | `{"msg":"设备登陆中","code":-10000}` | ❌ 否 |
| 37783 | 403 | `{"msg":"用户不存在或超时，请重新登录","code":-10000}` | ❌ 否 |
| 36027 / 38321 | 超时 | — | ❌ 否 |

为什么 405 是正确指纹：`/websock/*` 这个 location **只接受 WS 升级**，
明文 POST 在 nginx 的 method 层就被挡掉（405），根本到不了应用层；
所以 body 里那句 `bad token` 是"没带 JWE 头"的必然结果，**和 vhost 对错无关**。

而 403 那几个是**别的业务 vhost 的鉴权层**（"设备登陆中"是登录态检查），
它们也回 JSON、也是 `code:-10000`，看上去很像命中 —— 只看"是不是 JSON"就会误收。

## 五、进房验证

在 37679 上对 `live_in=1` 且 FLV 探活通过的房间做真实 join：

```
=== 房间 87839418 menu=102 ===
  join status=200 code=0
   [17.4s] room_msg  赢钱点仨美女: @備胎呆賊_ztnp 看见内裤了吗
   [18.6s] room_msg  年少金魚_szetch: 下注 120 元
  → 20s 内收到 130 条推送
```

推送有三类 `ctl`，我们只取 `room_msg`：

| ctl | 内容 | 处理 |
|---|---|---|
| `room_msg` | 聊天 / 礼物 / 下注 / 开奖 | 按 `content.typ` 分类，只留 32·4（聊天）和 3（礼物） |
| `room_player` | 进场用户（每次都带完整用户对象，几十条一批） | 丢 |
| `room` | 房间元信息变更 | 丢 |

`room_player` 占了推送量的大头（130 条里约 110 条），**必须丢**，否则列表会刷屏、
解析开销也白花。

| 文件 | 改动 | 为什么 |

| `data/LiveRepo.kt` | `wsJoinReachable` 判据改成 **405 为准、403+bad token 兜底** | 原判据是 `responseCode !in 200..299 → false`，真端口回 405 被直接判死，命中列表**永远为空** |

| `data/LiveDanmaku.kt` | 状态文案 `已进房 :37679` | 设置页一眼看出走的哪个端口 |

## 七、排查手册（下次再 404 先看这三行）

1. 设置页「弹幕」那行显示 `已进房 :XXXXX` → 正常，端口就是它
2. 显示 `:端口 join 回 404（试了 N 个端口）` → 候选全错，看下一行端口列表
3. 端口列表只有 1~2 个 → 说明 `groupPorts` 和 `/proc` 都没拿到端口，
   是隧道没起来（看「隧道」面板）而不是弹幕的问题
