## 2. 六个可直接复用的方法论

这六条比具体字段更有价值，换个同类 App 一样能用。

### 2.1 「找不到域名」时，先确认是否根本不需要域名

**症状**：静态产物里搜不到 API host，只有 `http://kiwi_hd` 这类占位符。

**判断依据**：config 里同时存在 `kiwi_starts = "kiwi_,127.0.0.1"` 这样的替换规则。

**结论**：这类 SDK 会把占位符 host 替换成 `127.0.0.1:<随机端口>`，业务流量走**本机回环隧道**，由原生层代理到真实上游。所以：

- 抓包不要抓 `wlan0`，抓 `lo`；
- 握手请求在 `lo` 上是**明文**的，token、路径全部可读；
- 端口每次启动随机，必须动态枚举。

这一条适用于所有「域名加密 / 域名动态下发」类加固，比硬逆 SDK 省一个数量级的工作量。

### 2.2 用「同一条通道内明文与密文共存」定位加密边界

**观察**：同一个 `/tunnel/` 前缀下有三条分支——`/tunnel/open?z=1` 是 zlib 明文，`/tunnel/<8hex>` 和 `/go/<blob>` 是密文。

**推论**：如果加密在原生层（libkiwi.so），三条分支应该密文程度一致。明文分支存在，说明**加密发生在 Dart 层，加密的是「路径 + body」，不是传输通道本身**。

**价值**：直接判定「不需要破解加固 so」。事后 IDA 分析也印证了这点——libkiwi.so 里有效字符串只有 3 条，加密逻辑不在这里。

**通用做法**：先找一条能出明文的同类请求，用它反推加密层级，再决定要不要动加固。

### 2.3 服务端「静默回退」是最大的调试陷阱

**症状**：请求返回 200、`code=0`、有数据，但数据永远是同一批 / 永远是默认值。

**实测案例**：

| 写错的东西 | 服务端行为 |
|---|---|
| `menuId`（应为 `menu_id`） | 忽略未知字段，返回默认列表（博彩区） |
| 未知分页参数 | 忽略，返回第 1 页 |
| 未知 body 字段 | 可能让整个 body 回退到默认 |

**排查手法**：拿同一接口打两次，只改一个参数，**比对返回的 id 集合是否变化**。如果两次完全一致，说明这个参数没被识别——而**不是**「两类数据恰好相同」。

**这次的代价**：整整一晚上拿的都是默认列表，用户看到「全是游戏广告」才发现。

### 2.4 路径名和字段名存在多版本，报错码会骗人

**案例**：

```
/room_push/join  → -5003     ← 不是「参数错」，是「路径不存在」
/websock/join    → 200       ← 同一功能的当前命名
```

服务端对不存在的老路径返回的是**业务错误码**而不是 404，看起来像鉴权/参数问题，实际是路径过期。

**通用做法**：卡在某个错误码上超过 15 分钟，就换一次思路——先确认「这个路径在这个版本里还存在吗」，再去调参数。抓一次 App 自己的真实请求是最快的验证方式。

### 2.5 不要用「副作用探测」代替「元数据」

**错误做法**：并发拉 342 个房的视频流，能拉到就算真人直播间。

**为什么错**：它测的是「此刻有没有在推流」。下播的真人房会稳定 I/O error，被人误判成假房；而 `on_air=1` 的 342 个房里 109 个拉不到流，说明 `on_air` 本身不可信。

| | 拉流探测 | 元数据分类 |
|---|---|---|
| 耗时 | 60–90 秒 | 1.5 秒 |
| 时效 | 快照，10 分钟后一半不准 | 实时 |
| 准确性 | 混淆「身份」与「在线状态」 | 用平台自己的分类 |
| 副作用 | 342 次外部连接 | 9 次 API 请求 |

**正确做法**：优先找平台自己的分类字段（`/lobby_menu/list` + `menu_id`），副作用探测只能做兜底。

### 2.6 响应匹配必须看协议细节，不能想当然

**案例**：`/websock/*` 的响应帧**不带 `random`**，而普通接口带。

客户端按 `random` 匹配响应，结果 join 的响应永远匹配不上，看起来像「请求无响应」。抓包一看，响应明明回来了，只是没有 `random` 字段。

**通用做法**：换了新接口族，先用抓包确认响应帧的 schema，不要复用旧的匹配逻辑。

## 3. 数据层面的最终结论

### 3.1 官方分类（`/lobby_menu/list`）

```
真人区：5 新人 / 101 星秀 / 102 女神 / 103 颜值 / 104 交友 / 105 音乐 / 108 舞蹈
博彩区：8 游戏 / 8000~8013
```

每个分类「房间名带盘口词」的占比：

| menu_id | 分类 | 房间数 | 盘口名占比 |
|---|---|---|---|
| 104 | 交友 | 59 | 1.7% |
| 105 | 音乐 | 21 | 9.5% |
| 103 | 颜值 | 68 | 13.2% |
| 102 | 女神 | 62 | 19.4% |
| 101 | 星秀 | 62 | 25.8% |
| 108 | 舞蹈 | 36 | 36.1% |
| 8 | 游戏 | 34 | **85.3%** |

### 3.2 哪些字段是废的（都逐个验过）

| 字段 | 实测 | 判定 |
|---|---|---|
| `stream_flag` | 237 个有值的全是 0，105 个无此 key | 废弃 |
| `flag` | 同上 | 废弃 |
| `on_air` | 341/342 都是 1 | 不可信 |
| `live_in` | 340/342 都是 1 | 不可信 |
| `desc` / `pic` / `expires_time` / `new_chess_id` | 全空或全 0 | 废弃 |
| `chess_id` | 是「当前挂的玩法」，真人主播也挂快三 | 不能当身份判据 |
| `sex` | 只有统计相关性（可拉流里 sex=2 占 92%） | 不能当规则 |

**接口里没有任何字段直接标记「这是不是真人」**。能用的只有 `menu_id`（平台分类）+ 房间名特征。

### 3.3 状态字段的可用子集

| 字段 | 含义 | 可信 |
|---|---|---|
| `player_count` / `count_list` | 在线人数 | ✅ |
| `live_fee` + `live_pay_type` | 付费房票价与支付方式 | ✅ |
| `battle_id` | 连麦（PK）中 | ✅ |
| `city_show` | 主播城市 | ✅ |
| `title_id` | 房间头衔 | ✅ |

## 4. 已知边界（没解决的）

| 边界 | 表现 | 可能的方向 |
|---|---|---|
| `/room/list` 不可分页 | 每分类固定 50 条，`pageIndex`/`page`/`offset`/`limit`/游标类全部无效 | 抓 App 翻页时的真实请求体 |
| 房间上限 300 | 7 个分类去重后的并集 | 同上 |
| 弹幕只能读，不能发 | 未尝试发送链路 | 需要 `content_type`/`optcode` 的反向构造 |
| token 会过期 | App 重启/重新登录后 32hex 变化 | 需要自动化重抓（切网 + tcpdump） |
| 头像 403 | `attachment_url` 域名不在 RTMP 域上 | 找图片 CDN 的真实 host |
| HTTP-FLV / HLS 403 | 该域名只开放 RTMP | 本地网关已绕过 |

## 5. 怎么跑

```bash
# 起网关 + 托管页面
python tools/gateway.py
# 浏览器打开 http://127.0.0.1:8899/

# 需要刷新房间列表时
python tools/build_site3.py

# 不进页面，直接看某个房间的实时弹幕
python tools/live_ws.py watch <room_id> 1 60
```

不启网关也能双击 `site/index.html`：分类、搜索、列表、弹幕都正常，播放区会提示启动网关。

## 6. 一句话

**这次真正的收获不是「拿到了接口」，而是「确认了三件事都不需要做」：不需要找 API 域名、不需要破解加固 so、不需要靠拉流猜测房间类型。**

前四个小时大部分工作都花在这三件「不需要做」的事上。找到正确的观察点（`lo` 回环明文 + 平台分类字段）之后，剩下的都是机械工作。
