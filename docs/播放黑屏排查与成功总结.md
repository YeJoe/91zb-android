# 直播黑屏根因定位与原生播放器实现总结

> 时间：2026-10-28 ~ 2026-10-29
> 目标：用原生方式（不用 WebView）播放 91 直播的 FLV 流
> 结果：**成功**。根因是 CDN 对视频载荷做了差分 XOR 混淆，与解码器无关。

---

## 一、结论先行

黑屏不是解码器选错、不是分辨率不对、不是丢帧策略问题，也不是封装"不标准"。

**流里的视频 NALU tag 被 CDN 做了可逆的差分 XOR 混淆：**

| 项目 | 规则 |
|---|---|
| 触发条件 | tag 首字节 ∈ `{0x18, 0x28, 0x1d, 0x2d}` |
| 首字节含义 | 真实 codecId **加 1**（H.264 I 帧 `0x17→0x18`、P 帧 `0x27→0x28`；H.265 I 帧 `0x1c→0x1d`、P 帧 `0x2c→0x2d`） |
| 载荷变换 | 从下标 2 起 `密文[i] = 明文[i] XOR 明文[i-1]` |
| 还原入口 | `明文[1]` 恒等于 `1`（AVCPacketType = NALU），可从前往后顺推 |
| 影响范围 | 只有视频 NALU tag；序列头（hvcC）和音频 tag 不混淆 |

还原之后，126 个视频 tag 全部解析成合法 NAL 链（VPS / SPS / PPS + IDR），ffmpeg 一次性解出 544×960 的真实画面。

**没还原之前，任何解码器都不可能出画**：首字节 `0x1d` 是 codecId 13，没有模块认识它；载荷又是 XOR 后的乱码，既不是 Annex-B 也没有合法的长度前缀。所以之前 MediaCodec 手写解封装、ExoPlayer、LiteAV 全部黑屏是必然结果，不是参数没调对。

## 二、时间线：每一步试了什么、看到什么

### 阶段 1：正面硬写 MediaCodec（失败，但修掉三个真 bug）

自研 FLV 解封装 + MediaCodec + SurfaceView 直出。现象：**音频正常出声，视频解码器 configure 成功，渲染帧数恒为 0**。

这一阶段虽然没解决问题，但修掉了三个真实缺陷，后面一直在用：

| 问题 | 现象 | 原因 | 修法 |
|---|---|---|---|
| 完全没有声音 | `setupRawAudioFormat: incorrect numChannels: 0` | FLV 音频 tag 里采样率/声道传了 0 | 从 AAC 的 ASC 解析出真实采样率与声道（44100Hz 1ch / 48000Hz 2ch） |
| 软解 configure 失败 | `Wrong cropped rect (0,0,0,0) vs. frame (0,0)` | `MediaFormat` 宽高传 0×0，硬件解码器能从 SPS 自取，软件解码器不行 | 自己解析 SPS 拿真实宽高（544×960） |
| 有画面纹理但全黑 | csd 与帧格式不配套 | 帧已转 Annex-B，csd 却塞了整块 hvcC | hvcC 拆成 VPS/SPS/PPS 三个独立 NAL 作 `csd-0/1/2` |

### 阶段 2：换现成播放器（全部失败）

- **ExoPlayer**：0 帧。
- **LiteAV 8.9.10355**（Maven 免费播放器版）：`startPlay ret=0`，码流能收到，音频能出，视频 0 帧。
- 顺手逆向原版 APK：发现它用的是**自研 LivePlayer 插件**（Flutter MethodChannel `LivePlayer`，TextureView 外部纹理），并不是腾讯云 / ijk / media_kit 这类第三方 SDK。这否掉了"照抄原版 API 调用"的捷径——它的解封装在自己 native 代码里。

### 阶段 3：WebView + jessibuca(WASM) —— 第一个决定性证据

把网页端同一套 `jessibuca.js + decoder.js + decoder.wasm` 打进 assets，用 `WebViewAssetLoader` 以 https 源托管，纯 WASM 软解。

**能出画。** 分辨率 544×960、15~16fps、视频 100~270kbps 稳定。

这条证据的价值不在"能用"，而在于：同一条流、同一台设备、同一个网络，**只有 WASM 的解封装能解**。这就把问题从"设备或网络"锁定到了"我们的字节处理"。

### 阶段 4：把流拆到字节级

抓原始 FLV 做二进制分析，逐条记录：

| 观察 | 数据 |
|---|---|
| 文件头 | `FLV` + version 1 + flags，正常 |
| 序列头 tag | 首字节 `0x1c` → frametype=1, codecId=12（HEVC），hvcC 结构完整可解析 |
| 关键帧 tag | 首字节 `0x1d` → frametype=1, codecId=**13**（不存在） |
| 普通帧 tag | 首字节 `0x2c` → frametype=2, codecId=12（HEVC NALU），看着正常 |
| ffmpeg 直接读 | `Video codec (d) is not implemented`，`Error splitting the input into NAL units` |
| Annex-B 起始码 | `00 00 01` / `00 00 00 01` 在关键帧载荷里命中 **0** 次 |
| 长度前缀 NAL 链 | 4 字节大端长度，从 offset 0~15 任意起点都拼不成完整链（`off == len` 从不成立） |
| 帧间一致性 | 前 **102 字节在所有关键帧中完全相同** |

最后一条当时被忽略了，其实是最强信号：随机垃圾数据不可能跨帧 102 字节一致，那只可能是**同一段明文经过同一种变换**。

### 阶段 5：转折点 —— 在 jessibuca 源码里看到四个常数

不再猜"标准是什么"，改成去看"能跑的实现做了什么"。在 `jessibuca.js` 的 FLV 解析里找到对视频 codecId 的判断，里面除了标准值还有四个数字比较：

```
24  40  29  45      // 十进制
0x18 0x28 0x1d 0x2d  // 十六进制
```

而标准 codecId 是 `0x17 0x27 0x1c 0x2c` —— **正好每个都加 1**。

顺着"首字节是真实值加 1"往下推：既然标志位被整体偏移了 1，载荷很可能也做了可逆变换。试最简单的可逆运算——差分异或：

```python
for i in range(2, len(b)):
    b[i] ^= b[i-1]
b[1] = 1        # AVCPacketType 恒为 NALU
b[0] -= 1        # 还原真实 codecId
```

一次命中。整段载荷瞬间变成 `00 00 00 01 40 01 ...` 开头的标准 Annex-B，ffmpeg 直接出画面。

### 阶段 6：落成 Kotlin，原生链路出画

把还原逻辑写进 `FlvLivePlayer.deobfuscate()`，接回原来的 MediaCodec 链路，出画。WebView 降级为"设备没有 HEVC 解码器"时的兜底。

## 三、混淆算法（可直接移植到其他语言）

```kotlin
/** 视频 NALU tag 的差分 XOR 还原 */
private fun deobfuscate(data: ByteArray) {
    val b0 = data[0].toInt() and 0xFF
    // 只对四个"加密标记"生效，其余（序列头 0x1c、音频 tag）原样放过
    if (b0 != 0x18 && b0 != 0x28 && b0 != 0x1d && b0 != 0x2d) return

    var prev = 1                      // 明文[1] 恒为 1
    for (i in 2 until data.size) {
        val plain = (data[i].toInt() and 0xFF) xor prev
        data[i] = plain.toByte()
        prev = plain
    }
    data[1] = 1
    data[0] = (b0 - 1).toByte()       // 还原真实 codecId
}
```

对应的 Python 验证脚本（可独立跑）：

```python
def deobf(b):
    b = bytearray(b)
    if b[0] not in (0x18, 0x28, 0x1d, 0x2d):
        return b, False
    for i in range(2, len(b)):
        b[i] ^= b[i-1]
    b[1] = 1
    b[0] -= 1
    return b, True
```

**注意三点：**

1. 序列头（首字节 `0x1c`）**不能**参与还原，它是明文。这正是最初误判的源头——序列头能解析，关键帧不能，看起来像"只有 I 帧坏了"。
2. 必须从下标 2 开始，下标 1 是要强制置 1 的包类型字段，不参与异或链。
3. 还原可原地做，无额外内存分配；每帧 O(n)，37KB 的 I 帧约几十微秒，可忽略。

## 四、为什么之前所有线索都指向了错误方向

这一节比算法本身更值得记，因为下次遇到类似问题还会踩。

| 看到的证据 | 当时的判断 | 实际含义 |
|---|---|---|
| ffmpeg 报 `Video codec (d) is not implemented` | 封装不合规，需要私有解封装器 | `0xd` 就是被 +1 后的 codecId，是混淆的直接指纹 |
| MediaCodec `configure` 成功但 0 帧 | csd 或分辨率不对 | 解码器根本收不到合法 NAL，configure 只看 format 不看帧 |
| 普通帧 `0x2c` 看起来正常 | 只有 I 帧被私有编码 | P 帧也被混淆（`0x2c→0x2d`），只是它偶尔能被容错跳过 |
| 网页端能播、原生不能 | 浏览器有特殊解封装能力 | 不是"浏览器"特殊，是 **jessibuca 的 JS 里就写着还原逻辑** |
| 5 个房间 × 原画/720/360 全一样 | 服务端某路流坏了 | 全线都在混淆，所以"换房间换清晰度"这条路永远无效 |

**核心教训：当"看起来是编码问题"但所有解码器都不认时，先怀疑字节被改过，而不是怀疑解码器能力。**

## 五、最终架构

```
HttpURLConnection 拉 FLV
        │
        ├── FLV tag 解封装（9B 头 + 11B tag 头 + 24bit ts + 4B prevSize）
        │
        ├── 视频 tag ──> deobfuscate（差分 XOR 还原）
        │                   │
        │                   ├── hvcC 拆 VPS/SPS/PPS ──> csd-0/1/2
        │                   │
        │                   └── 长度前缀 NAL → Annex-B → MediaCodec
        │                                            └── SurfaceView（零拷贝直出）
        │
        ├── 音频 tag ──> ASC 解析采样率/声道 ──> MediaCodec(AAC) ──> PCM ──> AudioTrack
        │                                                                  （主时钟）
        │
        └── 失败兜底 ──> WebView + jessibuca(WASM)
                         触发条件：CODEC_FAIL / 首帧 8s 超时 / 三档清晰度全失败
```

## 六、可复用的排查方法论

1. **先找"同一份数据在别处是什么结果"。** jessibuca 能播这一条，把搜索空间从"整个播放链路"压缩到"我们的字节处理"，价值超过前面所有尝试。
2. **不要预设格式是标准的。** 先 dump 原始字节：首字节长什么样、相邻帧首字节是否成规律、是否单调偏移。
3. **去搜魔数，不要搜格式文档。** 能跑的实现里那四个常数（`24/40/29/45`）比任何官方规范都管用——它们是"这个私有实现认哪些值"的直接答案。
4. **穷举验证必须有硬判定标准。** 判断"长度前缀 NAL 链是否成立"用的是 `off == len`（整段精确消耗完）。随机数据满足这个条件的概率接近 0，所以结论可靠；如果只看"N 个 NAL 头长得像"，就会得出错误结论（我一度以为 `40 01` 命中 1 次是 NAL，其实是因为 37KB 里 2 字节特征随机命中期望值就有 0.57 次）。
5. **跨帧一致性是强信号。** 102 字节完全相同 → 不是随机垃圾 → 一定是同一种可逆变换。
6. **失败要分层归因。** "有声音没画面"先分三层：解封装产出的 NAL 对不对 → 解码器收没收到 → 有没有 release 到 surface。之前一直在这三层之间来回猜，直到把每层的日志都打出来才定位。
