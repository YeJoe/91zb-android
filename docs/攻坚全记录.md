## 1. 完整时间线

### 阶段一：改工具路线（19:00 – 22:00）

**卡点**：Frida 挂不上，`spawn` 直接崩，`attach` 显示进程存在但注入后无回调。

**排查过程**：
1. 以为是包名/版本问题，换 `frida -U -f`、`frida -U -n` 两种方式，都失败。
2. 看 `ps -A` 发现 App 进程架构是 **arm64**，但设备本身是 x86_64（MuMu）。
3. 结论：跑在 **Houdini arm64 翻译层**上。Frida 的 arm64 gadget 注入 x86 容器时无法完成 inline hook，这是已知限制，不是配置问题。

**转向**：放弃动态注入，改两条静态路线并行：
- `strace` 看系统调用（拿到 fork/exec 与 socket 行为）
- `tcpdump` 抓包（最终承担了全部取证工作）

同时尝试过 GitHub 下载 Frida server 资产，卡在下行速率上（几十 KB/s），进一步确认这条路不值得投入。

**阶段产出**：`docs/BASE与TOKEN获取方案.md`、`docs/MuMu抓包指南.md` 的实操部分。

---

### 阶段二：先解决「有没有接口」的问题（22:00 – 23:30）

**动作**：确认隧道就是明文反向代理。

- 从 `pp.txt`（blutter 反汇编）找到 `_ApiInfoManager` 与 `ApiUrls.dunUrl / dunKey / dunKiwiStart`。
- 发现 config 里 BASE 全是占位符：`http://kiwi_hd`、`kiwi_im/tunnel/open?z=1`。
- 关键常量：`kiwi_starts = "kiwi_,127.0.0.1"` —— SDK 会把 `kiwi_` 前缀的 host **替换成 `127.0.0.1:port`**。

**第一次认知修正**：
> 不存在「真实 API 域名」这个东西。
> 客户端根本不用域名访问业务接口，它连的是本机回环上的隧道进程。
> 之前所有「找域名」的努力方向都是错的。

同一阶段解出 RabbitCipher 的 key/iv 派生和路径混淆（`docs/加密方式分析.md`），但当 `/tunnel/open?z=1` 的明文帧被抓到之后，这套加密分析对当前目标就没必要了——**加密只作用于 `/tunnel/<8hex>` 和 `/go/<blob>` 两条分支**。

---

### 阶段三：明文通道打通（23:30 – 00:30）

**卡点 1**：`/login/init` 用普通 HTTP 请求，一律返回「仅支持长连接」。

**试过**：19 种 query 参数与 header 组合（`?token=`、`Authorization`、`X-Token`、`appversion` 各种传法），全部失败。

**转机**：既然它自己说「只支持长连接」，那就不该用 HTTP 打。改成走 WebSocket 的 `/tunnel/open`，帧格式：

```
上行 {"body":{},"random":N,"method":"POST","uri":"/login/init"}
下行 {"opt":"http","data":{"status":200,"random":N,"body":"<转义 JSON>"}}
```

一次通，拿到 47KB 的 init 数据（user / config / notices / 背包）。

**卡点 2**：pcap 解析工具自己写错了三处，排查花了不少时间：
- RTMP 握手有 3073 字节需要跳过，否则 AMF0 解析全乱；
- chunk 是 128 字节边界，跨块要按块头规范重组，`0xc3` 是续块标记；
- 流名前面那个 `0x6d` 是长度前缀字节，不是流名的一部分（一度把流名读成 `m45383697`，实际是 `45383697`）。

**卡点 3**：`/login/init` 里**没有 RTMP 域名**。翻遍 47KB 的 config、notices、背包数据都没有。

**结论**：域名不在业务接口里下发，只能从 RTMP 握手里抓（`docs/视频流拉取方案.md`）。抓到的域名经过多次冷启动验证，**是平台级固定的，不是会话级**。

**阶段产出**：`tools/tunnel_api.py`、`tools/rtmp_sniff.py`、`tools/pcap_streams.py`、`docs/明文长连接通道.md`
**副产物**：`proof_noauth.flv`（110 万字节，零鉴权拉流实证）、`proof_frame.jpg`（首帧）

### 阶段四：卡在进房 -5003（00:30 – 00:43）

这是当晚最长的一段死路。

**现象**：`/room_push/join` 恒返 `-5003`，而同一通道上的 `/websock/leave`、`/websock/change_pay_type` 都正常返回。

**逐一排除**：
1. 怀疑接口废弃 → 试 `/websock/join_room_new`，404。
2. 怀疑版本号 → 试了 5 种传法（query、header、body 字段、`appversion`、`version_code`），全无效。
3. 怀疑登录态 → 重新登录、换 token，无效。
4. 怀疑房间属性 → 换 6 个不同 `chess_id` / `menu_id` 的房，全部 -5003。
5. 怀疑通道 → 换端口、换明文/密文分支，无效。

**还做了一件走偏的事**：服务端返回的文案是「請前往系統設定 > 更新版本」。我一开始以为这是客户端 Dart 代码里弹的，去 `pp.txt` 的字符串池里搜这句话——**搜不到**。这说明文案是服务端下发的透传内容，「找 Dart 处理逻辑」这条路根本不存在。

**转机**：用户手动进房，抓到 `join2.pcap`。解析后发现真正的进房调用是：

```
uri = /websock/join
body = {"room_id":<id>,"menu_id":3,"cp_type":3}
```

`/room_push/join` 是**更早版本**的命名。改路径，一次通过，返回 `player_count=7564` 和 27 个在场用户。

### 阶段五：把 token 彻底搞清楚（00:43 – 00:59）

路径改对之后仍然报 `{"code":-10000,"msg":"bad token, please login!"}`，说明卡在鉴权。

**发现 token 是分层的**：

| token | 来源 | 能干什么 | 在 `/websock/*` 上 |
|---|---|---|---|
| quick-login 的 32hex | `/login/quick` 明文接口 | 普通业务接口（`/index/hello` 200） | ❌ 报 bad token |
| JWE（330 字符） | App prefs 的 `token` 字段 | `Authorization: Bearer` 头 | 必须带，但光有它不够 |
| App 会话 32hex | **只能抓包** | 隧道 URL 的 `?token=` | ✅ 唯一有效 |

**App 会话 token 的拿法**（这条是当晚最关键的一步）：

```bash
# 在设备上抓回环接口，触发 App 重连（切 WiFi 或强制停止后重启）
tcpdump -i lo -s 0 -A -l -q > /data/local/tmp/hs.txt
# 然后从明文握手里 grep
grep -ao "token=[0-9a-f]\{32\}" hs.txt | sort -u
```

因为隧道走的是 `127.0.0.1`，握手请求在 `lo` 接口上**完全明文**，`GET /tunnel/open?z=1&appversion=…&token=<32hex>` 直接可读。

**第二个坑**：`/websock/*` 的响应帧**不带 `random` 字段**。我们的客户端一直按 `random` 匹配响应，所以 join 永远拿到 `null`——看起来像「请求没回应」，其实是回了但没被认领。改成「发出去后的第一帧 http 就是响应」。

**第三个坑**：端口必须和 `/index/hello` 是同一台 vhost（实测 1406 / 37549）。其他端口返回 404 或 403，且 `/websock/*` 走普通 HTTP 一律 405。

**阶段产出**：`tools/live_ws.py`（join/hist/watch/leave 四命令）、`tools/wsframe.py`、`tools/wsdump.py`、`docs/直播接口清单.md` 第 11 节

### 阶段六：第一版网页——数据全错（01:00 – 01:15）

**动作**：`tools/build_site.py` 抓 `/room/list` 3 页 × 16 个 `menuId`，产出 50 个房 + 87 条弹幕，写成静态页。

**用户当场指出**：这些全是游戏/广告直播间，不是真实直播间。

**复盘**：
- 16 个 `menuId`（0~15）返回的是**同一批 50 个房**，说明参数根本没生效；
- 这批房的名字全是「XX快三」「XX百家乐」「真人倍投」；
- 也就是说，服务端一直在返回**默认列表**，而默认列表以博彩区为主。

**第一反应**：以为 `/room/list` 只返回博彩区，需要找别的接口。于是扫了 2529 条路径（`tools/api_scan.py`），找不到分类接口。

**转机**：`/lobby_menu/list` 返回 34 项官方分类。分类 id 是 5/101/102/103/104/105/108（真人区）和 8000~8013（博彩区）。

**但按 id 请求仍然返回同一批房**。又试了 12 种参数名（`menu`、`type`、`class_id`、`area_id`、`tag_id`、`cid`、`category_id`…），全无效。

**真正的根因**：

```
❌ {"pageIndex":1, "menuId":103}    ← 驼峰，服务端不认识
✅ {"pageIndex":1, "menu_id":103}   ← 下划线，正确
```

服务端遇到不认识的字段**不报错、不回退报错**，而是静默使用默认值。所以 `menuId` 这个错写法看起来「请求成功」，实际上一直在读默认列表。

改一个字符，7 个分类返回**完全不同的房间集合**。

**阶段产出**：`tools/build_site3.py`、更新版 `docs/真人直播间筛选.md`

### 阶段七：数据质量——把广告房剔出去（01:15 – 01:33）

分类对了，但每个分类里仍混着「名字带盘口词」的房（如「一家人百家乐」「毛毛虫倍投时时彩」），占比 1.7% ~ 36.1%。

**先试了错误方法：批量拉流探测**（`tools/probe_stream.py`，342 房 / 16 并发，60–90 秒）。

结果 232/342 可拉流，看起来能用。但**这个判据是错的**——它测的是「此刻有没有在推流」，不是「是不是真人」：

| 房间 | 名字 | 在线 | 拉流 |
|---|---|---|---|
| 167047514 | 性瘾🍼小野猫 | 177 | ❌ I/O error |
| 1662310139 | 极品静静 | 141 | ❌ I/O error |
| 1916430984 | 可爱的丽娜 | 40 | ❌ I/O error |

这些明显是真人主播（只是下播了）。反过来 `on_air=1` 的 342 个房里，109 个根本拉不到流 —— `on_air` 字段本身在说谎。

**然后把所有疑似状态字段逐个验了一遍，全是废的**：

| 字段 | 实测 | 可用性 |
|---|---|---|
| `stream_flag` | 237 个有值的全是 0，105 个连 key 都没有 | ❌ |
| `flag` | 同上 | ❌ |
| `on_air` | 341/342 都是 1 | ❌ |
| `live_in` | 340/342 都是 1 | ❌ |
| `desc` / `pic` / `expires_time` / `new_chess_id` | 全空或全 0 | ❌ |

**最终方案**：不用拉流做分类器。分类只用官方 `menu_id`，广告房靠「房间名含盘口词」做一次轻量标记（`ad=1`），页面默认隐藏、可一键显示。这样：
- 取数据从 60–90 秒降到 **13 秒**；
- 判定依据从「网络状态快照」变成「平台自己的分类 + 名字特征」，不会随时间过期。

### 阶段八：播放层，两个兼容性坑（01:36 – 01:45）

**坑 1**：浏览器内核不支持 RTMP。这是内核能力问题，不是代理问题，无解。

**坑 2**：该域名的 HTTP-FLV / HLS 全返回 **403**。说明这条链路只开放了 RTMP，HTTP 侧被 ACL 挡住了。所以「拼一个 http://域名/live/xxx.flv」这条路彻底不通。

**方案**：本地网关 `tools/gateway.py`，用 ffmpeg `-c copy` 把 RTMP 转封装成 HLS（不转码，几乎不占 CPU，实测 2~4%）。

**坑 3（差点漏掉）**：HLS 清单出来了、分片也能下载，但页面还是黑的。原因是 **Chrome/Edge 桌面版没有原生 HLS 支持**（只有 Safari 有）。必须引入 `hls.js`。本地放了一份 `site/vendor/hls.min.js`（414KB），不依赖 CDN。

**坑 4**：清单解析成功但首帧迟迟不出来时，页面会一直是黑屏。加了「停滞检测」：9 秒没有画面就自动换路并给出提示。

## 2. 三条主线的解法对照

### 2.1 「域名」这条线

| 尝试 | 结果 |
|---|---|
| 在 `pp.txt` 字符串池搜 `http://`、`https://` | 只有占位符 `http://kiwi_hd` |
| 反编译 `_ApiInfoManager` 找 hosts 配置 | 拿到结构，但值就是占位符 |
| 解 prefs / sembast | 没有任何 API host |
| 扫 2529 条路径找下发接口 | 不存在这个接口 |

**最终答案**：
- 业务接口**没有域名**，只有 `127.0.0.1:<port>` 本地隧道，端口每次启动随机；
- 只有 **RTMP 推拉流**有真实域名，且只能从 RTMP 握手里抓，平台级固定、不随会话变。

### 2.2 「token」这条线

从「一个 token」变成「三条 token 各管一段」：

1. **quick-login 32hex** —— 明文 HTTP 接口能拿，管普通业务；
2. **JWE 330 字符** —— prefs 里能拿，管 `Authorization` 头；
3. **App 会话 32hex** —— 只能抓 `lo` 回环明文，管隧道 URL。

第 3 条是全场最难的一步，因为它不在任何持久化存储里，只在内存中、每次登录重新生成。

### 2.3 「进房」这条线

```
/room_push/join          → -5003（路径名是旧版本）
/websock/join_room_new   → 404
/websock/join            → 200 ✅
```

服务端对未知路径返回的不是 404 而是业务错误码 `-5003`，这一点很有误导性：看起来像「参数不对」，实际上是「路径不存在」。

## 3. 失败路径清单（避免重复踩）

| 路线 | 为什么放弃 |
|---|---|
| Frida 注入 | arm64 App 跑在 x86 容器的 Houdini 翻译层，gadget 无法 inline hook |
| `idat.exe -A -S` 批处理 | 用户环境的插件 import PySide6 导致崩溃；改用 idalib |
| 破解 libkiwi.so | 段名伪装 `.note.gnu.proc`、9467 个导出全乱码、有效字符串仅 3 条；**且加密不在这一层** |
| 从 Dart 找报错文案 | 「請前往系統設定」不在字符串池里，是服务端透传 |
| 普通 HTTP 打 `/websock/*` | 一律 405，必须走 WS 隧道 |
| 自己 quick-login 的 token 打 `/websock/*` | `bad token, please login!` |
| 用拉流判断真人/广告 | 测的是推流状态，不是身份；下播的真人房会被误杀 |
| 拼 `http://域名/live/xxx.flv` | 403，HTTP 侧被 ACL 挡住 |
| 找 `/room/list` 的分页参数 | `pageIndex`/`page`/`offset`/`limit`/游标类全部无效，传未知字段还会让请求体整体回退 |
