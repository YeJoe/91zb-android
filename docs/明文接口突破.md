## 0. 一句话结论

**不需要破解 `/go/` 的路径加密，也不需要安装天美。**
隧道出口是一台普通 nginx/openresty 反向代理，**明文 REST 路径可直接访问**；游客登录走明文 `POST /login/quick`，直接返回 32 位 token，随后 `POST /room/list?token=...` 就能拿到真实房间列表。

```
POST /login/quick  {apns_code,...}  ->  {"code":0,"token":"f801776a93b0cdc035bd9d28b70022da", ...}
POST /room/list?token=<token>  {}   ->  {"code":0,"has_next":1,"result":[12311998, 268611990, ...]}
```

## 1. blutter 输出先做定性：这是"混淆版 + 方法体缺失"的产物

| 指标 | 数值 | 含义 |
|---|---|---|
| dart 文件 | 997 | 顶层没有 `data_center/` 等可读目录 |
| 类名 | `xS` `yS` `cMt` `DMt` | 全部混淆，`class :: {}` 空名 |
| 库 url | `// lib: , url: adt` | **连 library url 都被混淆了** |
| 方法体存在 | 2135 | 可读汇编 |
| 方法体缺失 | 4550（`size: -0x1`） | **2/3 的函数没有输出** |

关键影响：想找的加密闭包，恰好全在"缺失"那一档：

```dart
// asm/DMt.dart  —— class yS 就是 HttpTunnelLive4
class yS extends tS {
  static late final k kxi;                     // offset: 0x14ac
  [closure] Uint8List <anonymous closure>(dynamic, dynamic) {
    // ** addr: 0x1533148, size: -0x1        <- 空
  }
  [closure] Uint8List <anonymous closure>(dynamic, dynamic) {
    // ** addr: 0x15330bc, size: -0x1        <- 空
  }
}
```

两个返回 `Uint8List` 的匿名闭包 = 路径加密/解密的实现位点（一个给 `/go/`，一个给 `/e/`）。
**方法体为空 ⇒ 这份 dump 拿不到算法本体。** 但对象池（`pp.txt`）是完整的，常量能挖出来。

## 2. 从 pp.txt 挖到的新常量

### 2.1 盾配置的解密密钥换成了原始字节数组

```
[pp+0x421f8] TypeArguments: <syb, Null?>
[pp+0x42200] String: "AES/ECB/PKCS7"                       <- 算法没变
[pp+0x42208] List<int>(32) a1 18 27 68 fe ce 23 5c ...    <- 新 key #1 (32B)
[pp+0x42210] List<int>(32) c9 24 61 13 7e 46 ac c6 ...    <- 新 key #2 (32B)
[pp+0x421d8] String: "ApiUrls.dunUrl"
[pp+0x421e0] String: "ApiUrls.dunKey"
[pp+0x421e8] String: "ApiUrls.dunKiwiStart"
```

8.1.7 里是 ASCII 字符串 `56c51dbc887d0487f942e6fca95108e4`；8.5.3 改成两个 32 字节数组（一解一验/一主一备）。

十六进制（另存 `tools/dun_keys.txt`）：
```
key1 = a1182768fece235c01744986c0a40f34bf9f43d62bd907f57926abdc3657064f
key2 = c92461137e46acc67006e5347931c8f9162ea76fde15d12fa43346281f660d5f
```

### 2.2 旧 SALT 已被删除

`jQBUO&2pfS5sC」¥\?AtglXv*w+PcRK8%i`（8.1.7 用于 `md5(SALT+hour+token)`）在 8.5.3 的字符串池里**完全不出现**。
同区域改成了字节数组：`[pp+0x5b600] List<int>(35)` 与 `[pp+0x5b608] List<int>(35)`。
（35 字节 = 31 字符 + 两个 3 字节符号，形状与旧盐一致，但**不是合法 UTF-8**，说明存的是加密后的盐或异或表。）
⇒ `rabbit.py` 的 `KEY_SALT` 对 8.5.3 **无效**，这是之前请求全部 404 的根因之一。

### 2.3 路径载荷结构：末尾 13 字节明文尾

实测报错 `encrypted api path too short: 23 bytes`（当时明文是 10 字符的 `/room/list`）:
```
23 - 10 = 13   ⇒ blob = 混淆(path) + R2(13 字节)   —— 与 8.1.7 结构一致
最短 24 字节   ⇒ 明文路径最短 11 字符
```
但提取密钥失败：周期性约束求解在 11/13 双周期下无解（复合周期 143 > 样本长度 118），
说明**双重异或的两个 key 都是每次随机**，无法从密文反推。**这条路放弃是对的。**

### 2.4 路径清单规模

pp.txt 里以 `/` 开头的接口路径 **581 条**，其中 REST 风格（以 `/` 结尾）**42 条**：
`/room/list` `/room/get_info_by_ids` `/login/quick` `/login/hello` `/stream/generate_agora_token`
`/chat/list_chat_ids/` `/message/latest/` `/relationship/followees/` …

## 3. 决定性发现：隧道就是明文反向代理

App 把 HTTP 打到 `127.0.0.1:<随机端口>`，`libkiwi.so` 加密后经 `121.204.228.227:7001` 转发。
`adb forward` 把该端口映射到 PC 后，**明文请求直接抵达后端**，返回标准 nginx 响应头。

**每个端口 = 隧道里的一个上游 vhost**（同一端口不同路径还可能分到不同服务）：

| 端口 | Server | `POST /room/list` | `POST /login/quick` | 判断 |
|---|---|---|---|---|
| 21547 | nginx/1.24.0 | **200** 房间号数组 | **200** 返回 token | ★ 目标网关 |
| 42413 | nginx/1.20.1 | **200** 房间号数组 | **200** 返回 token | ★ 同源备用 |
| 22729 | nginx/1.24.0 | 403 用户不存在或超时 | — | 另一租户 |
| 42845 | nginx/1.20.1 | 403 用户不存在或超时 | — | 另一租户 |
| 27392 / 38921 | openresty/1.25.3.1 | 403 设备登陆中 | 403 | 另一租户 |
| 35842 / 45961 | openresty/1.21.4.2 | 405 bad token | 405 | H5 会话型网关 |
| 6981 / 22250 / 37273 | nginx | 404 | 404 | 静态/资源 vhost |

port 会随 App 活动动态增删（一次启动 19~37 个），**必须先探活再请求**。

## 4. 游客登录（明文，无需装天美）

```bash
# 1) 找可用端口
python tools/json_api.py ports

# 2) 游客登录（apns_code = prefs 里的 machine id，同 device 复用同一账号）
python tools/json_api.py login --device 29e9eb7c-b442-350b-b325-3427cd26f85b \
    --pkg com.l95c2450d7.f68bb4e2d5 --channel ecy --version 8.5.3
# -> TOKEN: f801776a93b0cdc035bd9d28b70022da  (昵称 包子臉哈哈_xxx, ID 2094967700, 渠道 ecy)

# 3) 拉房间列表
python tools/json_api.py rooms --size 20

# 4) 任意接口
python tools/json_api.py call /room/list '{"page":1,"page_size":5}'
```

原始请求形态：

```http
POST /login/quick?token= HTTP/1.1
content-type: application/json
user-agent: Dart/3.10 (dart:io)

{"apns_code":"29e9eb7c-...","app_name":"live3","package_name":"com.l95c2450d7.f68bb4e2d5",
 "channel_id":"ecy","device_type":"android","version":"8.5.3"}
```

响应（`data` 里 30+ 字段：`id/nickname/avatar/level/bloc_id/channel_id/login_type/mobile/...`）：

```json
{"code":0,"is_new":false,"token":"04af20de6a726c89c5ad957376eca1ca",
 "data":{"id":2094967700,"nickname":"包子臉哈哈_...","bloc_id":"ecy",
         "hosting_channel":"ecy","channel_id":"ecy","level":1, ...}}
```

### 关键点

- **字段名是 snake_case**：`apns_code` 而不是 `apnsCode`（用驼峰会返回 `apns_code is null`）。
- **缺 `apns_code` 单独传会 RST 断连**（`RemoteDisconnected`），必须带全 6 个字段。
- token 每次登录都会重新签发（同一账号不同值），旧值不失效。
- 这个 32 位 hex token **不是** prefs 里那个 JWE，两者属于不同鉴权体系：
  - 32 hex token → 明文 JSON 网关（`?token=`）
  - JWE → `/go/` protobuf 网关（`Authorization: Bearer`）

## 8. Frida 可行性判定（2026-10-28 实测）

**结论：Frida 在这台 MuMu 上不可用，且已无必要——`strace` 等价且更省事。**

### 8.1 原因是 Houdini ARM 翻译层

| 观测 | 值 |
|---|---|
| 设备 ABI | `x86_64,arm64-v8a,x86`（`ro.dalvik.vm.isa.arm64=x86_64`） |
| 目标进程加载的 so | `/data/app/.../lib/**arm64**/libapp.so`、`libflutter.so`、`libkiwi.so`、`libliteavsdk.so` |
| 翻译器 | `/system/bin/houdini64`、`/system/lib64/libhoudini.so` |
| guest 运行时 | `/system/lib64/arm64/libc.so` |

进程是 **x86_64 宿主 + arm64 guest**。Frida 的 Interceptor 按宿主架构改写指令，无法作用于被翻译执行的 arm64 代码；注入 arm64 agent 同样不行（目标进程是 x86_64）。所以 `libapp.so`（Dart AOT）、`libkiwi.so`（盾+隧道）这两层**都 hook 不到**。

### 8.2 frida-server 也下不来

主机有 `frida` 17.5.0 CLI，但设备无 frida-server；GitHub release 资产经当前代理 20 s 卡死（`curl: (56)`，0 字节）。

### 8.3 替代方案：strace（已实测跑通）

`/system/bin/strace` 存在，KernelSU root + SELinux permissive，**ptrace 附加后进程存活，盾未反制**。syscall 层与架构无关，guest 的 `write/sendto` 一样看得到。

```bash
PID=$(adb -s emulator-5554 shell pidof com.l95c2450d7.f68bb4e2d5 | tr -d '\r')
adb -s emulator-5554 shell "su -c 'strace -f -p $PID -e trace=network,write -s 3000 -o /data/local/tmp/st.txt >/dev/null 2>&1 &'"
# 触发一次 App 行为
adb -s emulator-5554 shell "su -c 'pkill -f strace; grep -a -oE \"(GET|POST) [^ ]+\" /data/local/tmp/st.txt | sort | uniq -c | sort -rn'"
```

实测输出（token 每次冷启动重新签发，与历史值不同属正常）：

```
2 POST /game_club_member/get_money?token=<APP_TOKEN>
2 GET  /tunnel/open?z=1&appversion=20260226001&token=<APP_TOKEN>
2 GET  /tunnel/a033b072?z=1&nobase64=1&token=<APP_TOKEN>
2 POST /api/v2_5/android/eomuw20g//stats/events?hwef=zQ&f3ef=...   (13 个随机短参)
```

### 8.4 仍未解决的那一步不是插桩问题

缺的不是"看到请求"，而是"让 App 去请求详情"。Flutter 在 MuMu 上渲染黑屏，`uiautomator dump` 拿到的只有 launcher 桌面（App 未真正前台），因此**UI 驱动**才是唯一未解环节。

## 9. 房间详情接口打通（8.5.3，2026-10-28 实测）

### 9.1 采集方式：tcpdump on lo（不用 frida，见 §8）

```bash
# 起抓包（注意 pkill 必须单独一次调用，否则 pkill -f tcpdump 会杀掉自己这条 shell）
adb -s emulator-5554 shell "su -c 'pkill tcpdump'"
adb -s emulator-5554 shell "su -c 'nohup tcpdump -i lo -s 0 -A -l -n > /data/local/tmp/lo.txt &'"
adb -s emulator-5554 shell am force-stop com.l95c2450d7.f68bb4e2d5
adb -s emulator-5554 shell am start -n com.l95c2450d7.f68bb4e2d5/.MainActivity
```
冷启动 20 秒即可拿到完整请求头 + 请求体。App 的请求长这样：

```
POST /game_list/list?token=<32hex> HTTP/1.1
user-agent: Dart/3.10 (dart:io)
content-type: application/json
transfer-encoding: chunked
accept-encoding: gzip
authorization: Bearer <JWE>   <- JWE，330 字符
host: 127.0.0.1:<隧道端口>

{"is_inside":0,"channel_id":"ecy"}
```

即：**路径不加密、body 是明文 JSON**（因为 App 用了 `?z=1&nobase64=1`），
`token` 走 query，`JWE` 走 authorization，两者同时带。

### 9.2 关键结论：`get_info_by_ids` → `get_list_by_ids`

旧清单里的 `/room/get_info_by_ids` 在 8.5.3 是 **404**（路由不存在）。
挨个试出来的正确接口：

```
POST /room/get_list_by_ids?token=<32hex>
{"ids":"25999068,208073602"}          -> {"code":0,"rooms":[...]}
```

三个坑，全部实测：

| 写法 | 结果 |
|---|---|
| `{"ids":"25999068,208073602"}` 逗号串 | ✅ 全命中 |
| `{"ids":[25999068]}` 数组 | ❌ `rooms:[]`，**不报错、静默忽略** |
| `{"ids":"[25999068,208073602]"}` JSON 数组串 | ⚠️ 只解析出部分（3 个里出 2 个） |
| `{"roomIds":[...]}` 等错字段名 | ❌ `{"code":-1,"msg":"ids is null"}` |

`Room` 字段（19 个）：
`id, name, menu_id, on_air, live_in, live_fee, live_pay_type, player_count, city, city_show,
sex, chess_id, new_chess_id, battle_id, battle_info_id, title_id, has_guang_nian, attachment,
attachment_db_url, attachment_url`

### 9.3 鉴权差异（这是之前卡住的真正原因）

| 接口 | `?token=` | `authorization: Bearer JWE` | 缺失时的报错 |
|---|---|---|---|
| `/room/get_list_by_ids` | 必需 | 不需要 | — |
| `/room/list` | 必需 | **必需** | `{"code":-2,"msg":"查询类型错误"}` |

「查询类型错误」是**鉴权失败的伪装**，不是 menuId 传错。之前把 menuId 从 0 试到 100 全部失败，
就是因为缺 JWE。补上 JWE 后 `{"pageIndex":1,"menuId":0}` 直接 200 返回 50 个房间。

响应可能 gzip（`raw[:2] == b'\x1f\x8b'`），需解压后再 json。

### 9.4 仍然挡着的：进房

`POST /room_push/join?token=...` 在 token/JWE 齐全、body 带 roomId/userId/version 的情况下，
一律返回 `{"code":-5003,"msg":"請前往系統設定 > 更新版本"}` —— 服务端版本闸，
参数（version/appVersion）已在 body 里试过，判定要看 header 或另有签名。**下一步待解。**

## 10. 视频流已打通（2026-10-28 23:5x）

**播放是标准 RTMP，且服务端零鉴权。流名就是房间号。** 详见 `docs/视频流拉取方案.md`。

```bash
python tools/rtmp_sniff.py cap 40     # 抓一次，拿到加速域名
ffplay "rtmp://<域名>/live/<房间号>"   # 之后任意房间直接拉
```

三个推翻旧假设的实测结果：

1. 之前认为「必须解 join 才能拿流地址」——**错**。地址由客户端用「服务端下发的域名 + 房间号」拼成。
2. `token` / `liteavToken` / `t` 看起来是鉴权，**实际服务端完全不校验**：去掉全部参数照样出流。
3. 服务器 IP 直连不行（按 vhost 路由），所以域名不可省；域名不在 prefs、不在 Dart 字符串里，只能抓。

证据：`125.77.147.203:1935` 下行 11.2 MB；上行仅 3704 B（握手 3073 + AMF0 命令），
`connect.tcUrl` / `FCSubscribe` / `play` 全明文；录制 6 秒得 91 帧 h264 720×1280 + aac 48k。
