# 源 App（天美 8.5.3）如何确认「在播」——冷启动实测

> 实测时间：2026-10-30 13:40
> 设备：MuMu（Android 15 / vivo V2245A，KernelSU root）
> 目标：`com.l95c2450d7.f68bb4e2d5`，versionName **8.5.3**
> 方法：`am force-stop` → `am start` 冷启动，前后各导一次 `FlutterSharedPreferences.xml`，对比 25 秒内服务端推送造成的状态变化；再用拉流探活交叉验证。
> 原始数据：`.tmp_analysis/`（prefs_before/after、maps、net_tcp、脚本）

---

## 0. 结论

**源 App 不确认。** 没有任何探活、没有 HEAD/Range 预检、没有「列表→可用性」过滤。

它的「在播」完全等于 **服务端 WS 推送里的 `live_in` 字段**，落在本地表里；大厅只是对这张本地表做
`menu_id` 过滤 + 人气排序。真正的「能不能出画面」它也不提前判断，而是**进房后拉流失败才提示**。

所以源 App 的大厅里同样有大量点进去「主播不在线」的房间——它展示的是**主播库**，不是**在播列表**。

---

## 1. 冷启动实测：本地表 + 推送增量

冷启动前后各取一次 prefs，房间表键为：

```
flutter.localData:room.<uid>      # uid=423344474，单条 JSON 字符串，约 1.7 MB
```

| 时刻 | 房间数 | 文件大小 |
|---|---|---|
| 冷启动前 | 2230 | 3 075 684 B |
| 启动后 25s | **2248** | 3 089 973 B |

25 秒内发生的变化（这是「实时性」的直接证据）：

| 变化 | 数量 |
|---|---|
| 新增房间 | +18（全部 `live_in=1`、`on_air=1`） |
| 字段被更新 | 167 |
| └ `live_in` 翻转 | 33（样本均为 0 → 1） |
| └ `player_count` | 165 |
| └ `expiresTime` | 165（中位数 ≈ 当前时间 − 47s，说明就是推送时刻） |
| └ `live_fee` | 12 |
| 删除房间 | 0 |

对应文档 §11.3 的推送帧：`{"opt":"u","ctl":"room","data":{"id":<room>,"live_in":1,...}}`
和 `{"opt":"u","ctl":"video","data":{"id":<room>,"player_count":N}}`。
**全程没有任何「拉列表」的请求**（`/room/list` 已下线），本地表就是列表。

## 2. 本地表的字段分布（2248 条）

| 字段 | 分布 | 含义判断 |
|---|---|---|
| `on_air` | 1 × **2209**，0 × 21 | 房间维度：**几乎恒为 1，不能用来判在播** |
| `live_in` | 1 × 1568，0 × **662** | 唯一会翻转的布尔：**这才是「此刻在播」** |
| `player_count` | 2047 个不同值（最大 10w+） | 实时人气，推送刷新 |
| `stream_flag` | 1 × 1754，3 × 475，0 × 1 | 流类型/清晰度标记，与可播性弱相关 |
| `expiresTime` | 每次推送刷新为「当前时间」 | 推送心跳，不是流过期时间 |
| `menu_id` | 104×471、101×374、8×317、102×191… | 房间自身分类（8=游戏） |

**关键：`on_air` 与 `live_in` 是两个维度。** 我们现网筛的是 `on_air==1`，等价于「不筛」——
2209/2248 都会通过，其中 662 间 `live_in=0`（已下播）也照样进列表。

## 3. 探活交叉验证：403 就是「此刻没推流」

对 `<domain>/live/<房间号>.flv` 发 `Range: bytes=0-15`，只认 `FLV` 三字节：

| 分组 | 样本 | 可播 | 说明 |
|---|---|---|---|
| 冷启动刚被推送刷新过的房 | 60 | 22（37%） | `live_in` 刚被服务端确认为 1 |
| 陈旧 `live_in=0` 的房 | 40 | 2（5%） | 基本确认已下播 |
| 全池随机 | 100 | 8（8%） | 任意时刻真实在推流的比例很低 |

不可播的一律是 `HTTP 403` + `Server: NgxFence`（不是超时、不是 404）。

**403 是房间级的，已排除三种猜测：**

1. 不是域名/IP 池问题：抓包里 6 次真实播放用了 6 个**不同随机子域名**
   （`kw386n16jo7wnztv` / `j77zw9agdp05fc41` / `fhpxge851qgo4wf4` …），
   实测同一房间在 7 个不同子域名下结果一致；能播的房在所有子域名下都是 200。
2. 不是代理导致：绕过本机代理直连结果相同。
3. 不是模拟器网络差异：在设备内用 `nc` 手打同样的请求，同样是 403。

**附带发现：** 抓包里每次 RTMP 连接的子域名前缀（16 位随机）都不同，且不同前缀解析到
**不同的边缘 IP 组**（`125.77.147.201/208/220/223` vs `125.77.147.214/222` + `222.186.20.x`）。
这是 DNS 层的负载均衡，不是鉴权；对我们「能不能播」没有影响，但对「连到哪个边缘」有影响。

## 4. 源 App 的三层「判定」其实是三层兜底

| 层 | 做法 | 代价 |
|---|---|---|
| 大厅列表 | 本地表 + `live_in`，`menu_id` 过滤、`player_count` 排序 | 会展示已下播但还没收到 `live_in=0` 推送的房 |
| 点卡片 | 直接进播放页，不预检 | 用户点进去才知道在不在播 |
| 进房后 | 取流失败 → 提示「主播不在线 / 直播已结束」 | 一次失败体验 |

它没有「保证列表里都是能播的」这个目标，所以也没有我们遇到的这个问题。

## 5. 对我们的直接结论

1. **没有服务端「在播列表」接口**——`/room/list` 已下线，`get_list_by_ids` 只是按 id 查详情，
   其中 `on_air` 恒 1、`live_in` 也以 1 为主（600 条样本只有 5 条 0），单靠接口字段筛不干净。
2. **403 = 不在播**，我们现有的「读到 `FLV` 才算活」判据方向是对的，不需要推翻。
3. 真正的问题是**筛选后剩多少**：任意时刻全池真实在推流的只有 ~8%，`live_in=1` 的子集约 37%。
   我们感觉「90% 播不了」，是因为列表基数取了 2248 个主播，而不是 200 个在播。
4. 可落地的两步改进（都不需要新接口）：
   - 先用 `live_in==1` 做第一道筛（免费，接口里就有），把 662 间明确下播的挡掉；
   - 再对剩下的做**可见窗口**探活（不是全量、也不降并发），结果 20 分钟 TTL 复用，
     可播置顶、探死沉底压暗（不删房间）。
5. 若要做到源 App 那种「实时」，可以复用我们已有的隧道 WS：冷启动 25s 内服务端就推了 167 条
   房间更新，说明大厅级订阅是可行的——用它维护本地 `live_in`，再探活校验。

### 5.1 实施记录（2026-10-30）

已按上面第 4 条落地，但**没有采纳「并发降到 8」**：全池 1972 间 ÷ 8 并发 × ~0.5s ≈ 2 分钟以上，
比原来 24 并发慢 3 倍，且射频满载时间更长、更费电；而 403 已证实是**房间级**而非限频
（换子域名、绕代理、设备内手打结果一致），降并发换不来任何收益。实际做法：

| | 改前 | 改后 |
|---|---|---|
| `live_in` 预筛 | 无 | `live_in==0` 软筛（筛完 < 8 间就整批放行） |
| 探活范围 | 全量 1972 间 / 轮 | 可见区间 + 40 张预取，单批上限 160 |
| 重复探活 | 5 分钟一次全量 | 同一间 20 分钟内不重复（手动刷新才清） |
| 前台/播放中 | 照探 | 不探（`onResume/onPause` + `openIndex`） |
| 结果用途 | 直接删房间 | 可播置顶、探死沉底 + 压暗，不删 |

代码位置：`LiveRepo.toRoom/fetch`（预筛）、`AppContainer.onFeedVisible/ensureProbed`（窗口探活）、
`HomeScreen.FeedPage`（上报可见区间 + 三档排序）、`RoomCard.dim`（压暗标「未在播」）。
