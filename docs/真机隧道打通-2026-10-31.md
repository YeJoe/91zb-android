> 关键突破：真机那份 **7.14** 的 App，明文隧道端口是可直接访问的 HTTP 服务，
> 真号 token 完全有效。读接口全部打通，**不需要 frida，不需要碰加密通道**。

## 一、怎么找到的

1. `tcpdump -i any` 抓包，发现两条关键流：

```
127.0.0.1:43706 -> 127.0.0.1:41047
GET /images/128/avatar/system_v3/....jpg HTTP/1.1
user-agent: Dart/3.10 (dart:io)
host: 127.0.0.1:41047
```

→ App 用 Dart HttpClient，所有 HTTP 都走本机回环，**且是明文 HTTP**。

2. `ss -ltnp | grep saas.i18n` 发现 App 进程（`saas.i18n:stub1`）监听了 21 个本地端口。

3. 用 `adb forward` 把这些端口映射到 PC，逐个 `POST /user_follow/my_follow` 试探：

| 端口 | 空 token 响应 | 判定 |

| 64850 | `403 {"code":-10000,"msg":"设备登陆中"}` | 设备级通道 |
| 47733 / 60198 | `404 Not Found` | 有 HTTP 服务，不挂该路由 |
| 其余 | 超时 | 非 HTTP（Dart isolate 内部 IPC） |

```

```

`?token=` 和 `authorization: Bearer` **两个都要带**。响应可能是 gzip。

## 五、写接口：最终结论（已穷举，不必再试）

### 5.1 7.14 的 so 里确实有写路由

在真机这份 `libapp.so`（7.14，27MB）里能直接搜到：

```
/relationship/add            /relationship/remove
/relationship/followees      /relationship/followee_count
/relationship/follower_count /relationship/is_following
RelationshipMgr.addFollow:   RelationshipMgr.removeFollow:
followeeId                   channelId    tui1
```

路由候选共提取到 1182 条，**关注相关只有 `relationship/*` 和 `user_follow/*` 两组，没有第三个写入口**。

### 5.2 但它不在任何本地明文端口上

| 端口 | `/index/hello` | `/relationship/add`（带完整参数） | 判定 |
|---|---|---|---|
| **51637** | 200 `hello` | **404** | 业务 vhost，但不含 relationship |
| 64850 | 200 `hello` | 404 | 极简 vhost |
| 47733 / 60198 | 404 | 404 | 非业务 vhost |
| 41047 | 502 | 502 | 图片代理 |

关键判据：**51637 上 `/relationship/followee_count/` 也返回 404** —— 说明整个 `relationship` 模块不在这个 vhost，
不是单条路径写错。

### 5.3 `/user_follow/add` 是假接口（再次证实）

```
add {"followeeId":2015725571}                                  -> {"code":0}
add {"followeeId":2015725571,"userId":...,"channelId":"tui1"}  -> {"code":0}
add {}                                                          -> {"code":0}
count: 304 → 304（不变）
```

**空 body 也回 `{"code":0}`，三种参数返回完全一致** —— 网关兜底，不落库。与 8.5.3 时期的结论一致。

### 5.4 路径变体全排除

`/relationship/add/`、`/relationship/addFollow`、`/user_follow/follow`、`/user_follow/cancel`、
`/user_follow/remove`、`/user_relationship/add`、`/follow/add` —— **全部 404**。

### 5.5 关注请求不出网

抓包期间点了一次关注（服务端 count 从 303 → 304，**确认真的生效了**），但：

- 443 上只有 `obus-dc20123-cn.heytapmobi.com`（OPPO 统计），无业务流量
- 本地回环里 `relationship` / `follow` 关键字 0 命中
- 7710 是 CDN 图片，用**单字节 XOR 0x3E** 混淆（已破解：`GET /images/128/avatar/...`）
- 本地 `47696 -> 45637`（App 自己的 45637 端口）是**加密数据**，XOR 0x3E 解不开

→ **写关注走 App 内部的私有加密通道，且该通道不出网。**

### 5.6 结论

**明文层只有读，没有写。** 这不是版本差异，是架构如此：本地 HTTP 隧道（51637）只暴露读类模块，
写操作走进程内加密协议。

## 六、方案 A：UI 自动化关注 —— 已验证成功 ✅

既然明文层没有写接口，但 App 自己点关注是能成功的，那就**让 App 自己点**。

### 6.1 关注按钮在哪

直播间左上角主播信息条，昵称右侧的**实心爱心**（白色圆圈包裹的红色爱心）。

设备：OPPO PGZ110，1080×2412，density 480。

```
爱心中心坐标 ≈ (368, 173)
```

### 6.2 实测结果

| 步骤 | 关注数 |
|---|---|
| 点击前 | 304 |
| `adb shell input tap 368 173` | — |
| 点击后 | **305** ✅ |

点击后爱心按钮消失（变为已关注状态），服务端 count 实时 +1。

### 6.3 为什么能定位到按钮

Flutter 是自绘 UI，**`uiautomator dump` 拿到的控件树里所有 `text` 都是空的**，
没有任何 text / content-desc，无法用文本或 resource-id 定位。

只能靠截图 + 人工/图像定位坐标。步骤：

```bash
adb shell screencap -p /sdcard/s.png
adb pull /sdcard/s.png
# 用 Pillow 裁剪放大目标区域，读出像素坐标
python -c "from PIL import Image; Image.open('s.png').crop((180,100,520,280)).resize((1020,540)).save('crop.png')"
```

### 6.4 工具

`tools/ui_follow.py`：

```bash
python tools/ui_follow.py          # 点默认坐标并自动验证 count 变化
python tools/ui_follow.py 368 173  # 指定坐标
python tools/ui_follow.py --count  # 只查关注数
```

脚本会自动对比点击前后的 count，明确指出「关注成功 / 取消关注 / 点偏了」。

### 6.5 局限

1. **坐标与分辨率绑定**。换机型、改 UI、换直播间布局都要重新标定。
2. **依赖源 App 在前台**，且已登录真号。
3. **直播间没有统一的 intent 入口**（壳包没有 LAUNCHER activity，多开容器自己管理），
   目前只能在「已经打开的界面」上点击，无法直接跳到指定主播的直播间。
   要做「关注任意主播」，还得先解决「如何用 intent 打开指定房间」。
