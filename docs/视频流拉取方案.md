# 视频流拉取方案（天美 8.5.3 / 通道 ecy）

> 结论先行：**播放是标准 RTMP，且服务端不做任何鉴权。流名就是房间号。**
> 唯一需要动态获取的是「加速域名」，它由服务端在进房时下发，抓一次包即可。

---

## 1. 一句话用法

```bash
# ① 抓一次包（40 秒内点进任意一个直播间）
python tools/rtmp_sniff.py cap 40

# ② 之后任意房间，直接拉
ffplay "rtmp://<已记录的域名>/live/<房间号>"
python tools/rtmp_sniff.py record 736303908 30
```

实测地址形态：

```
rtmp://1dtluv36amaiuckq.7kv5kqq7k77g.hebeisaixin.com/live/45383697?token=<32hex>&t=<过期>&liteavToken=<uuid>
└──────────────── 加速域名，服务端下发 ────────────────┘ └app┘└房间号┘ └──── 鉴权参数，实测可全部省略 ────┘
```

## 2. 实测证据

### 2.1 抓包定位

`tcpdump -i any` 抓到 98 MB，其中视频：

| 方向 | 字节 | 说明 |
|---|---|---|
| `125.77.147.203:1935 → 10.0.2.15:34740` | 11 226 895 | **RTMP 下行，视频本体** |
| `10.0.2.15:34740 → 125.77.147.203:1935` | 3 704 | RTMP 握手 + 命令，全部明文 |

上行只有 3704 字节 = 握手 3073（C0 1B + C1 1536 + C2 1536）+ 命令 631，所以
**整个播放协商过程是可读的**。

### 2.2 RTMP 命令原文（AMF0 明文）

```
connect      tcUrl = rtmp://1dtluv36amaiuckq.7kv5kqq7k77g.hebeisaixin.com/live
createStream
FCSubscribe  45383697?token=e17a6b1e...&t=1793289341&liteavToken=1fc55ba4-...
play         45383697?token=e17a6b1e...&t=1793289341&liteavToken=1fc55ba4-...
```

服务端回：

```
Server: NgxFence
Video:  h264 (High), 720x1280, yuvj420p, progressive
Audio:  aac (LC), 48000 Hz, stereo, fltp
```

### 2.3 三段式验证（这是最关键的部分）

| 试验 | URL | 结果 |
|---|---|---|
| ① 原房间原参数 | `/live/45383697?token=…` | ✅ h264 720×1280 |
| ② **换房间号，沿用同一 token** | `/live/736303908?token=…` | ✅ 出流 → token 不绑房间 |
| ③ **完全不带鉴权参数** | `/live/45383697` | ✅ 出流 → **服务端根本不校验** |
| ④ 去掉 liteavToken | `/live/45383697?token=…&t=…` | ✅ 出流 |
| ⑤ 直连服务器 IP | `rtmp://125.77.147.203/live/736303908` | ❌ I/O error → 按 vhost 路由，域名必需 |
| ⑥ 换 prefs 里的其它域名 | `zb01.tv` / `pzhibo.tv` / `jrbanquan.com` 等 | ❌ 全部失败 |

④ 之后又做了批量验证，从实时房间列表里抽 3 个：

```
1150577440  → h264,720,1280 + aac  ✅
919803155   → h264,720,1280 + aac  ✅
1118877707  → I/O error  ❌（该房间未推流 / 非直播桌）
```

无鉴权录制复验：`736303908` 录 6 秒 → 1 104 219 字节、**91 帧真实画面**、aac 48k 立体声。

## 3. 为什么域名必须现抓

- `grep hebeisaixin FlutterSharedPreferences.xml` → **0 次**
- `grep hebeisaixin` blutter 的 `pp.txt` / `objs.txt` → **0 次**
- 所以既不在缓存里，也不在 Dart 字符串常量里 → **服务端下发**

补充：`localData:config` 47 KB 里能查到的是播放器 license 和聊天缓存开关，
所有域名类的键（`tencent_play_key` = `license.vod2.myqcloud.com`）都不是推拉流域名。
服务器是腾讯云 CSS 的私有加速域名（`Server: NgxFence` 为自建 nginx 媒体服务器），
随机子域是按账号/会话分配的。

> **更正（2026-10-29 实测）**：域名是**平台级固定域名，不是会话级的**。
> App 之后又冷启动过两次，同一域名依然可拉流（`1150577440`、`64378161` 均验证通过）。
> 所以只需**抓一次并存到 `.rtmp_domain.txt`**，之后长期可用。
> 早先「可能变、要重抓」的判断是错的。

## 4. 实现要点（踩过的坑）

### 4.1 必须跳过 RTMP 握手再解块

上行流前 3073 字节是握手，直接当块流解会立刻错位。

```python
if buf[:1] == b'\x03' and len(buf) > 3073:
    buf = buf[3073:]
```

### 4.2 AMF0 字符串会被切成多个 chunk

第一次手工截取时读到 `...b3ba-d5f4\xc35fd2c502`，那个 `0xc3` 不是数据，
是 **RTMP 续块头**（fmt=3，csid=3，1 字节）。因为默认 chunk size = 128，
109 字节的流名正好跨越块边界。

错误做法：`bytes(b for b in raw if b != 0xc3)` —— 能凑出 109 字节，但是碰运气。
正确做法：按 RTMP 块头规范重组消息（见 `tools/rtmp_sniff.py` 的 `parse_chunks`）。

### 4.3 别把长度前缀当成名字

AMF0 字符串是 `0x02` + 2 字节大端长度 + 内容。流名长度 109 = `0x00 0x6d`，
而 `0x6d` 正好是 ASCII 的 `m`，于是肉眼看到的是 `m45383697?…`，
误以为流名带个 `m`。实际流名是 `45383697?…`。

### 4.4 房间号本身就是流名

`45383697` 在 `localData:room` 里就是房间对象的主键：

```
"45383697": {"id":45383697,"name":"壹次性風之傷_tmdmwt","menu_id":103, ...}
```

`room_ids.1.3` 这个菜单列表里也包含它。所以不需要任何 ID 映射表。

## 5. 工具

| 文件 | 作用 |
|---|---|
| `tools/rtmp_sniff.py` | `cap` 抓包 / `parse` 解析 / `url` 拼地址 / `record` 录制 |
| `tools/pcap_streams.py` | 无依赖 pcap 解析 + TCP 重组 + TLS SNI 提取 |
| `tools/analyze_lo.py` | 解析 `tcpdump -A` 文本版（ASCII 有损，仅形态识别用） |
| `.rtmp_domain.txt` | `parse` 自动写入的加速域名 |

```bash
python tools/rtmp_sniff.py parse j.pcap
# RTMP 服务端 : 125.77.147.203 : 1935
# tcUrl/app   : ['rtmp://1dtluv36amaiuckq.7kv5kqq7k77g.hebeisaixin.com/live']
# 流名        : ['45383697?token=…&t=…&liteavToken=…']
```

## 6. 与之前结论的关系

之前卡住的 `/room_push/join` 版本闸（`code -5003 請前往系統設定 > 更新版本`）
**现在不再影响拉流**：播放地址不依赖 join 接口，只要拿到域名 + 房间号。

也就是说，之前那条「必须解进房接口才能拿流地址」的假设是错的 ——
播放地址是在客户端用「服务端下发的域名 + 房间号」拼出来的，进房接口不是必经之路。
